什么是 Solid？

Solid 是一个用 JSX 编写界面的 JavaScript 框架，语法接近 React，运行时模型却完全不同。它采用细粒度响应式：状态存放在信号（signal）中，读取信号的表达式会自动建立订阅，状态变化时只重新执行依赖它的那一小段逻辑。Solid 没有虚拟 DOM，JSX 在编译期被转换成直接的 DOM 创建和更新代码，因此更新可以细到单个文本节点或属性。本文从响应式原理讲起，依次覆盖状态管理、组件与 Props、条件与列表渲染、Effect 与 memo、Context、Store、Refs、Router 以及 createResource 数据获取，并在最后列出容易踩坑的注意点。

反应性

反应性指系统『自动响应』数据或状态变化的能力，目标是让界面与底层数据『保持同步』。

下面的计数器用 createSignal(0) 创建状态：它返回 [count, setCount]，其中 count 是 getter，必须写成 count() 才能取值；setCount 是 setter，既可以接收新值，也可以接收 prev => next 形式的更新函数。JSX 中只有 {count()} 这个文本表达式订阅了信号，点击按钮时 Solid 直接更新该文本节点，不会重新执行整个 Counter 函数。

这种写法和 React Hook 有相似之处，但语义不同：

  • createSignal() 对应 useState()，返回的是一对 getter/setter。
  • count() 对应 React 中的 count 变量，调用 getter 才是读取值并建立订阅。
  • Counter 函数只执行一次，状态变化不会让它整体重跑。

反应原理

信号 Signals

信号是响应式系统的核心，负责存储数据并在写入时通知订阅者。一个信号由两个函数组成：

  • getter：读取信号当前值。读取时如果处在某个订阅者的执行范围内，会把该订阅者登记为依赖。
  • setter：修改信号值，并触发依赖它的订阅者重新执行。

createSignal 接收初始值，返回 [getter, setter]。下面的原型只保留最小结构，用来说明 getter/setter 如何共享同一个闭包变量；真实实现还会维护订阅者集合、相等性判断和调度逻辑。

订阅者 Subscribers

订阅者负责『跟踪信号变化，并在信号更新时重新执行』。Effect、Memo 和组件的渲染表达式都属于订阅者。它的行为可以拆成两步：

  • Observation：执行时读取信号，从而被登记到该信号的订阅者集合中。
  • Response：信号写入后收到通知，重新执行自己，并重新收集依赖。

状态管理

状态管理是处理影响界面行为和展示的数据的过程，核心是存储与更新数据。Solid 用信号存储数据，用订阅者响应变化。

一个状态管理方案通常包含三个要素：

  • State：决定界面向用户展示什么的数据。
  • View：状态在界面上的表现。
  • Actions：修改状态的事件。

三者构成单向数据流：Action 修改 State，State 驱动 View 更新，View 不直接回写 State。

管理基本状态

状态是应用的唯一数据来源，决定界面展示什么。在 Solid 中，基本状态用 createSignal 表示，创建和读取方式与上一节的计数器一致。字符串、数字、布尔值这类不可变的基础类型适合放在 signal 中。

管理复杂状态

对象或数组这类嵌套结构用 createStore 管理更合适。Store 会为每个属性惰性创建信号，修改时通过路径定位，不需要手动展开整个对象。下一节会详细展开。

同步 vs 异步

同步反应性

同步反应性是默认模式。写入信号后，依赖它的计算和 effect 会在当前更新周期内按依赖顺序执行，读取到的是一致的新值。多次连续写入可以用 batch 合并，避免中间状态触发多余计算。

异步反应性

异步反应性指更新被延迟或分批执行，例如等待异步任务完成后再写入状态。当多个订阅者依赖多个信号时，延迟可以避免某个订阅者读到只更新了一半的数据。

Solid 提供 batch 把多次写入合并为一次通知，createResource 则把异步请求的结果包装成信号，让界面仍然按同步方式读取。注意：batch 延迟的是通知，不是把整个更新变成微任务。

关键概念（简单总结）

  • 信号负责存储和管理数据。
  • getter 和 setter 让信号既可读又可写。
  • 订阅者自动跟踪信号变化，并相应地更新系统。
  • 信号与订阅者协同工作，使系统与最新数据保持同步。
  • 反应式系统建立在数据驱动反应的原则之上。
  • 反应式系统可以是同步的，也可以是异步的。

组件

Solid 组件就是一个只执行一次的函数，返回 JSX。它没有类组件，也没有每次状态变化都重跑的渲染函数，因此不要把“组件函数会反复执行”的 React 直觉带进来。

事件处理程序

Solid 支持两种事件绑定写法：

  • on:click：把监听器直接加到元素上，等价于原生 addEventListener，称为本机事件。
  • onClick：把监听器委托到 document（或根节点），再按 JSX 树分发到目标元素，称为委托事件。

委托事件名不区分大小写，本机事件名区分大小写。由于 onClick 的监听器实际挂在根节点，原生 event.currentTarget 会是根节点；Solid 在分发时会临时把 currentTarget 指向绑定元素，所以读取 e.currentTarget.value 通常可用，但它不是浏览器原生赋的值。需要严格的原生语义时改用 on:click。

绑定事件

事件处理程序可以传数组，第一项是函数，第二项会作为函数的第一个参数传入，事件对象排在后面。这样不必使用 bind，也不会为每个元素创建额外闭包。

Prop Drilling 描述的是把 prop 一层层往下传、穿过许多中间组件的过程。Solid 的组件不拥有 state，但共享数据仍然可能需要在组件间传递，于是会出现同样的问题：中间组件被迫接收并转发自己并不使用的 props，重构困难，也容易产生不必要的耦合。

  • 避免多层级传递 props：常见做法是用 Context 把共享状态提供给深层组件，只有真正使用数据的组件才读取 Context。

列表呈现

Solid 提供 For 和 Index 两个列表组件，二者都接收 each，但 key 的选取方式不同。

For 标签

For 按数组元素本身（值或引用）做 key，适合列表顺序和长度频繁变化、每项有稳定身份的复杂数据结构。each 接收数组，或经 Object.entries()、Object.values() 处理后的对象数组。

回调接收两个参数：item 是当前项的值，index 是当前下标的信号，必须写成 index() 才能取值。

Index 标签

Index 按下标做 key，适合列表长度和顺序稳定、但元素内容频繁变化的场景。回调中的 index 是普通数字，固定不变；item 是信号，必须写成 item() 才能取到该下标的当前值。

Index 标签 vs For 标签

  • For：以元素本身做 key。
    • 列表值被替换、插入或删除时，会创建或销毁对应的行。
    • 仅交换顺序时，DOM 节点会跟随元素移动，不会整表重建。
    • 适合动态列表、元素有稳定身份的场景。
  • Index：以下标做 key。
    • 某个下标的内容变化时，只更新该行的 item 信号，其余行不动。
    • 插入、删除或重排会复用现有 DOM 行，并更新每行的信号值。
    • 适合长度稳定、内容频繁变化、元素是字符串/数字，或列表项包含输入框的场景。

ErrorBoundary 标签

ErrorBoundary 创建错误边界，捕获其子树在渲染或更新期间抛出的错误。渲染之外发生的错误，例如事件处理程序或 setTimeout 中的错误，不会被捕获。

fallback 用于在出错时展示提示。它可以是 JSX，也可以是回调函数，回调接收两个参数：

  • error：捕获到的错误对象。
  • reset：重置错误状态并重新渲染子项，让用户可以从错误中恢复。

管理依赖项

Solid 自动跟踪 effect 的依赖，不需要手动写依赖数组。effect 中读取的 signal、props、context 或其他响应式值，任何一个变化都会让它重新运行。

effect 初始化后一定会执行一次，即使没有依赖；之后只在依赖变化时再次执行。依赖是在执行时动态收集的，因此条件分支中未读取的信号不会成为依赖。

订阅信号

effect 读取信号时，会创建对该信号的订阅。一个 effect 可以订阅多个信号，多个 effect 也可以订阅同一个信号。

信号更新时，所有订阅者会按顺序收到通知。effect 是否执行、何时执行由调度决定，不能保证多个 effect 之间的执行顺序，因此不要让 effect 之间隐式依赖执行次序。

嵌套效果

嵌套 effect 各自收集自己的依赖，内部 effect 读取的信号不会注册为外部 effect 的依赖。因此内部 effect 更新时，不会导致外部 effect 重新执行。

实践

纯函数

Memo 的计算应当是纯函数：输出只由输入决定，不修改外部状态。在 memo 内部调用 createEffect 会创建嵌套 effect，容易造成重复订阅甚至无限循环；副作用应放到 createEffect 中。

将逻辑保留在memo中

派生状态放在 Memo 中，副作用放在 Effect 中。这样读取派生值的地方只依赖缓存结果，不会因为副作用再次触发更新。

Context

Context 用于在组件树中共享状态，避免一层层传递 props。官方文档见 Context。

何时使用？

  • 组件树很深，多个层级需要同一份状态，使用 Context 可以避免 prop drilling。
  • 多个组件需要定期访问同一份全局数据，例如当前用户、主题或国际化配置。

Refs

Ref 可以附加到元素或组件上，用于获取 DOM 元素或组件实例。

访问DOM元素

不建议通过选择器查找 DOM。Solid 中的元素会随状态增删，元素只有在挂载后才能访问，因此应在 onMount 中读取 ref，或使用回调 ref。

JSX作为值

可以把 JSX 赋给变量，再在需要的位置插入。这样可以复用同一段结构，但元素与组件其余 JSX 被拆开，可读性会下降。

注意：同一个 DOM 节点只能存在于一个位置，多次插入同一变量会移动节点而不是复制。

Solid 中的 Refs

在 JSX 中写 ref={myElement}，Solid 编译器会在创建元素后把元素赋给这个变量。变量在元素插入 DOM 之前就已经被赋值，因此不要在这个阶段读取布局信息。

信号也可以用作 refs

ref 也可以接收 signal 的 setter。组件首次渲染时元素可能还不存在，或稍后从 DOM 中删除，此时可以把 ref 放在条件分支内，只在元素存在时赋值。

转发refs

转发 ref 是把父组件的 ref 传给子组件，由子组件把它绑到内部元素上。父组件通过 props 拿到该 ref，效果类似 React 的 forwardRef，但在 Solid 中只是普通 prop，不需要额外 API。

指令

指令（directive）把可复用的行为附加到 DOM 元素上，使用 use: 前缀调用。一个元素可以挂多个指令，指令回调里可以创建信号、启动 effect 或添加事件监听。

指令本质是一个具有特定签名的函数：

  • element：应用指令的 DOM 元素。
  • accessor：读取传给指令的值的函数，值变化时 accessor 会返回新值。

指令函数在渲染时调用，但发生在元素插入 DOM 之前。

细粒度反应性

反应性让界面自动跟随数据变化，不需要手动更新 DOM。细粒度响应式把更新定位到具体属性或文本节点，而不是整个组件。

与 React 的差异：

  • Solid 更新发生变化的那部分 DOM，避免更大范围甚至不必要的更新。
  • React 重新执行整个组件函数来计算新的虚拟 DOM，再对比差异，单属性变化也可能带动整个组件重跑。

响应式原语

Solid 的响应式系统有两个关键角色：信号和观察者。在此之上还有几种原语：

  • Stores：代理对象，在后台按属性创建、读取和写入信号。
  • Memo：类似 Effect，但返回信号并缓存计算结果，适合计算优化。
  • resources：基于 memo，把网络请求的异步性转换为可在同步代码中读取的信号。
  • 渲染效果：一种立即启动的定制 effect，专门管理渲染过程。

验证反应式系统

管理反应式系统中的生命周期

反应式系统中的 signal、effect 等单元统称为节点，它们相互关联，共同构成响应行为。节点的创建、执行和销毁需要按固定顺序处理，否则会出现依赖丢失或重复订阅。

效果跟踪的同步性质

系统注册订阅者、执行 effect、再恢复订阅者，整个过程是线性同步的。如果在 createEffect 中启动 setTimeout，异步回调执行时全局的 currentSubscriber 已经恢复为 null，此时在回调里读取 getter 不会登记订阅，跟踪就会失效。

处理异步效果

基础响应式系统是同步的，框架在此基础上提供异步能力：

  • on：手动指定 effect 的依赖，适合需要显式控制触发时机的场景。
  • resource：把网络请求的结果包装进信号，让异步数据可以按同步方式读取。

注意点

  • getter 必须调用：createSignal 返回 [getter, setter]，取值写 count()，JSX 里写 {count} 会渲染函数本身。Store 的属性则相反，直接读 store.users，不要再加括号。
  • effect 不用于派生值：派生状态用 createMemo。用 createEffect 把结果写回另一个 signal 会多一次更新，依赖关系复杂时容易形成循环。
  • For 与 Index 的 key 不同：For 按元素值/引用做 key，元素替换会重建行；Index 按下标做 key，item 是信号，内容变化只更新对应行。列表项含输入框或长度稳定时优先用 Index。
  • mergeProps 与 splitProps 不要混用：前者合并默认值，后者把 props 拆成多组；两者都保留响应性。props 本身不要解构，解构会丢失后续更新。
  • 事件委托的差异：onClick 的监听器挂在 document，e.currentTarget 是 Solid 分发时临时指向绑定元素的，不是浏览器原生赋值；stopPropagation 也不会按元素层级生效，需要原生语义时用 on:click。
  • Store 的响应式读取：属性信号是惰性创建的，只有在组件、effect、memo 等追踪范围内读取才会订阅；unwrap 返回的是普通对象，修改它不会触发更新；produce 只适用于对象和数组。
  • SSR 注意：createEffect、onMount 不会在服务端执行，服务端渲染路径上不要直接访问 window、document；异步数据应通过 createResource 配合 Suspense 处理，避免在渲染期间发起无法等待的请求。
