结论先行

这篇记录 Git 实战中的几类高频问题：合并分支后时间线乱序、切分支被未追踪文件挡住、index.lock 残留、直接拉取远程其它分支时的游离 HEAD 提示，以及主干更新后如何同步到当前分支。核心做法是：团队统一用 rebase 合并，先改 pull.rebase 默认配置；时间线乱序用 reset + stash + pull 或交互式 rebase 重排；主干同步用 rebase master，冲突解决后 rebase --continue，最后按需强推。

背景与场景

当前公司业务是用 rebase 合并代码，则需要修改 git 拉取的默认配置。

先全局修改 pull 的默认行为为 rebase，避免每次拉取都产生额外的 merge 提交。

再查看配置是否生效，输出中找到 pull.rebase=true 即为成功。

下面的操作都在一个名为 studydemo 的练习目录里完成，每个子目录对应一个分支上的提交，先看清目录与分支的对应关系。

步骤一：解决合并分支的时间线乱序（feature5 合并 feature4）

现象是合并后提交时间线看起来乱序。下面三种方法按从简到繁排列，任选一种。

方法一：命令行重建提交

先撤回最新一次提交，暂存未提交内容，拉取最新代码后恢复暂存并重新提交，最后强制推送。

方法二：命令行 + TortoiseGit

先用命令行撤回最新一次提交，再在 TortoiseGit 里重新提交并合并上一次提交，最后强制推送覆盖远程。

方法三：交互式 rebase 合并提交记录

如果只是想把多条提交合并成一条、且没有删除分支等复杂操作，用交互式 rebase 最直接：先用 git log 拿到需要合并到的那个 commit id，再进入交互模式。

进入编辑器后按 i 进入可编辑模式，把需要合并的提交记录从 pick 改为 squash 或 fixup：

  • squash：将当前提交记录与上一提交记录合并，同时将提交信息合并为一个；
  • fixup：将当前提交记录与上一提交记录合并，但不保留当前提交记录。

改完按 esc，输入 :wq 退出，再修改合并后的提交信息并强制推送。

步骤二：处理切换分支时的 untracked 文件提示

切换分支时终端提示 The following untracked working tree files would be overwritten by checkout...，说明目标分支要写回的文件与当前未追踪文件冲突。按是否保留这些文件选择方法。

方法一：保留未追踪的文件

先把未追踪文件加入暂存并贮藏，执行完原本要执行的命令后再恢复。

方法二：不想要这些文件，直接覆盖

确认这些文件可以丢弃后，用 -f 强制切换，未追踪文件会被覆盖。

步骤三：清理 index.lock 残留

Git 操作被中断后，.git 目录下可能残留 index.lock，导致后续命令报错。直接删除该文件即可。

步骤四：直接拉取远程的其它分支（feature5 拉取 feature1）

在 feature5 上直接拉取 feature1 时，终端提示 (no branch, rebasing feature1)，说明仓库进入了游离 HEAD 的 rebase 状态。解决方案见下方链接，具体步骤以链接文章为准。

  • 解决方案：no branch, rebasing 解决思路（CSDN）

步骤五：主干有更新，但当前分支拉取时主干没变

场景是 master 已经更新，当前 feature 分支直接 pull 拉不到主干的内容。这里用 merge 会让时间线变乱，所以用 rebase，本质是把主干代码合并到分支。

先贮藏当前分支未提交的代码，确认分支后切到主干并更新。

切回要合并的分支，把当前分支变基到 master（变基后的内容在当前分支中更新）。

如果变基有冲突，按提示查看冲突文件（或看 VS Code 中标红的文件），解决后标记并继续。

查看日志，确认变基是否成功。

尝试普通推送到远程分支会失败（rebase 后本地和远程记录不同），需要强制推送。

最后弹出之前贮藏的代码。

分支都推送到远程后，把分支合并回 master

先在 master 上拉取最新记录，再 merge 目标分支，确认日志后推送。

注意点

  • git push -f / git push --force 会覆盖远程历史，只在自己独占的分支或团队约定允许时使用；多人分支优先确认后再推。
  • rebase 会重写提交历史，已经推送过的分支变基后通常需要强推，这也是「本地和远程记录不同」的原因。
  • git reset HEAD^ 只撤回最新一条提交，要撤回多条需把 HEAD^ 换成具体 commit id 或 HEAD~n。
  • 出现 index.lock 通常意味着有 Git 进程未正常退出，删除前先确认没有正在执行的 Git 操作。
  • 拉取远程其它分支出现 (no branch, rebasing feature1) 时不要直接删仓库，按解决方案处理。
