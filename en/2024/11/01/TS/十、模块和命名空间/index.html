结论先行

TypeScript 有两套组织代码的写法：模块（module）和命名空间（namespace）。早期文档把前者叫”外部模块”、后者叫”内部模块”，现在内部模块统一称”命名空间”，外部模块则简称为”模块”。实际项目应优先用模块：在顶层导出、只导入用到的名字、模块内部不再套 namespace；namespace 更适合小型项目，或在 .d.ts 里描述挂在全局变量上的老库（例如通过 script 标签加载的 D3）。这篇按”导入导出 → 编译目标 → 可选加载与第三方库声明 → UMD → namespace”的顺序把两套写法梳理一遍。

背景

TypeScript 早期的术语里，”内部模块”指的是用 namespace 包裹的一段代码，”外部模块”指的是一个文件通过 import / export 对外暴露内容。后来官方把内部模块改名为”命名空间”，外部模块直接简称”模块”。术语变了，边界问题没变：一段代码到底该写成文件级模块，还是写成全局的 namespace，取决于它要被谁、以什么方式使用。

步骤一：用 export 和 import 组织模块

导出声明的关键字是 export

要重新导出另一个模块的全部导出内容，使用 export * from 'module'。

导入一个模块的某个导出内容，并据此创建实例。

导入的重命名、整体导入与副作用导入

导入时用 as 给导出内容重命名。

把整个模块导入到一个变量，再通过这个变量访问模块的导出部分。

有些导入只为副作用，比如让模块设置全局状态供其他模块使用；这个模块可能没有任何导出，或者没人在意它的导出。

默认导出与 export = 语法

默认导出用 export default，它后面也可以直接跟一个值。

export = 语法用来支持传统的 CommonJS 和 AMD 工作流。它定义一个模块的导出对象，这里的”对象”指的是类、接口、命名空间、函数或枚举。要导入使用该语法导出的模块，必须使用 TS 的特定语法。

步骤三：可选模块加载与使用其他 JS 库

模块加载的核心是 import id = require("...") 语句，它能让我们访问模块导出的类型。为了确保类型安全，可以在表示类型的位置使用 typeof：此时得到的是一个类型值，这里就表示模块的类型。

Node.js 里大部分工作是通过加载一个或多个模块完成的，这类库的类型通常在 .d.ts 文件里定义。下面先用 declare module 声明 url 模块的形状，再用 import = require 引入。

加载模块有两种常见写法。方法一用三斜线指令引入声明文件，再按 ES6 规范导入。

方法二同样先引入声明文件，再按 CommonJS 规范导入。

如果只关心”这个模块存在”，可以用外部模块简写：只写模块名，模块里所有导出的类型都会是 any。

模块声明还支持通配符。SystemJS 和 AMD 支持加载非 JS 内容，可以用前缀 *! 或后缀 !* 来匹配。

步骤四：UMD 模块

有些模块被设计成兼容多个模块加载器，或者干脆不使用模块加载器（走全局变量）。这类库既可以通过 import 使用，也可以当作全局变量访问。

步骤五：用 namespace 划分作用域

命名空间的基本用法有三点：

  1. 一个模块里的多个子模块用 namespace name {} 包裹，里面的每个成员都使用 export 关键字暴露。
  2. 多文件中的命名空间，指的是同一个命名空间被拆分到不同文件，每个文件里被拆出去的部分外层都保留原来的命名空间包裹。
  3. 编译时，可以把所有输入文件合并成一个输出文件。

把所有输入文件编译成一个输出文件。

另一种方式是每个文件单独编译，然后在页面里用 script 标签按顺序引入。

简化命名空间操作的另一种方法是使用别名 import q = x.y.z。

步骤六：外部命名空间写在 .d.ts 里

有些程序库（例如 D3）在全局对象 d3 上定义功能，并且通过一个 script 标签加载，它的声明文件使用内部模块来定义类型。TS 编译器只有看到外部命名空间声明，才能识别这类库。

注意点

引用模块文件时应该用 import，而不是三斜线指令。

不要对模块使用命名空间，两者混用会让模块的边界失效。另外，指定的模块系统不同时，可能无法把多个模块源文件连接起来，这是选择模块系统时要考虑的成本。

尽可能在顶层导出，导入时只明确写出需要的名字。

如果只导出一个 class 或一个 function，直接用 export default 即可，不必额外包一层。

需要把整个模块当成一个对象访问时，用命名空间导入。

最后，模块里不要再使用命名空间。
