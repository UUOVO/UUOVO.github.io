结论先行：小程序的性能问题基本都能落回两个阶段——启动阶段（环境准备、代码注入、首屏渲染）和运行阶段（逻辑层与视图层之间的 setData 通信与重渲染）。所以优化也按这个顺序展开：先看启动流程里哪些节点可以压缩，再区分冷启动与热启动，最后按”启动期手段”和”运行期手段”逐项落地，包括骨架屏、分包异步化、虚拟列表、setData 合并、缓存与图片压缩等。

背景与场景

用户感知到的”小程序慢”，通常表现为点开白屏久、首页数据出得慢、列表滑动卡顿。这些现象对应的其实是不同阶段：白屏久多半在代码注入和首屏渲染，滑不动多半在 setData 传得太多或节点太多。因此先理解启动流程，再谈具体手段，才不会盲目优化。

一、启动流程

1. 环境准备

  • 小程序运行进程及运行环境的准备。
  • 代码包下载、校验及初始化。
  • 视图层系统组件、webview 容器和原生组件的初始化。
  • 逻辑层 JS 引擎初始化及域创建。

2. 代码注入

  • 框架及第三方基础代码的初始化 —— 小程序基础库、扩展库、插件、自定义组件。
  • 开发者代码注入：
    • 开发者逻辑层代码 —— 派发 App.onLaunch 以及 App.onShow 这些事件。
    • 开发者视图层代码 —— 公共代码以及页面代码的注入。

3. 首屏渲染

  • 逻辑层页面的初始化，这个时间点是 initDataSendTime 的一个触发时机，会派发 Page.onLoad 事件。
  • 视图层时间点走到 viewLayerReaderStartTime，会派发 Page.onShow 事件。
  • 开发者代码从后端拉取数据，准备 data 数据。
  • 页面的整体渲染。
  • 视图层时间点走到 viewLayerReaderEndTime，会派发 Page.onReady 事件，标志首屏渲染完成。

二、启动方式

1. 冷启动

用户设备上第一次打开小程序，或小程序被销毁后再次打开；以及进入后台『30 分钟以后』再次进入前台，都属于冷启动。

2. 热启动

小程序启动的一种优化机制：小程序进入后台『30 分钟以内』再次进入前台，可以直接从后台状态恢复到前台，前面的启动流程都不会执行。

三、具体优化手段

3.1 冷启动性能优化

涉及的应用生命周期函数

  • App.onLaunch：监听小程序初始化 —— 启动流程，一次性。
  • App.onHide：监听小程序切后台 —— 运行时性能。
  • App.onShow：监听小程序启动或切前台 —— 视图显示时派发，会重复派发与启动流程相关的事件，属于运行时性能。

涉及的页面生命周期函数

  • Page.onLoad：监听页面加载 —— 启动流程，一次性。
  • Page.onShow：监听页面显示 —— 视图显示时派发，会重复派发与启动流程优化相关的一次性事件。
  • Page.onHide：监听页面隐藏 —— 运行时性能。
  • Page.onReady：监听页面初次渲染完成 —— 启动流程，一次性。
  • Page.onUnload：监听页面卸载 —— 运行时性能。

顺着流程可优化的节点

  • 环境准备阶段、拉取小程序基本信息阶段 —— 拉取信息是同步的，用户使用越多启动性能越好，可提高轮询机制的命中率。
  • 紧跟小程序基础库更新 —— 提高预加载环境的命中率。
  • 代码注入阶段 —— 减少代码的注入量和复杂度，以期减少启动时间。
  • 合适的生命周期函数节点 —— 首屏渲染要从后端拉取数据并在首页渲染时，使用异步转同步的编程范式以及并发复合命令，在多个文件里对齐代码的执行点。
  • Page.onReady 时间派发、首屏渲染完成阶段 —— 使用动态数据加载的，可以采用骨架屏技巧、压缩图片、提高服务器接口响应效率和数据传输效率。
  • 数据预拉取和周期性更新机制 —— 微信提供了数据预拉取与周期性更新机制。
  • 低端机首次渲染需要较长时间的情况下 —— 微信提供了初始渲染缓存机制。

3.2 运行时渲染性能优化

双线程运行机制

  • 微信小程序可以看作由逻辑层、视图层两个线程协同完成运行。
  • 『逻辑层负责执行 JS 代码，视图层负责渲染 UI 页面。』逻辑层与视图层之间的事件触发以及数据传递，也就是『setData 方法的调用全是由底层的 Native 层负责中转完成的』。
  • 『setData 函数用于更新视图数据』。按照微信小程序的性能评判标准，setData 每次传递的数据大小不能超过 256KB，超过这个限制页面就容易卡顿。在页面或列表组件的 scroll 事件里频繁调用 setData，视图层来不及渲染，也会出现明显的卡顿。

冷启动与运行时都可用的优化技巧

  • 使用 WXS 脚本，在视图层完成事件处理。
  • 重渲染机制。
  • 支持 WXWebAssembly。
  • 允许开发者另开 Worker 线程 —— 针对 JS 是单线程执行。
  • 分页渲染、使用虚拟 DOM —— 针对长列表页面 setData 单次传递数据不能超过 256KB 的限制。
  • 使用 localStorage 接口把数据缓存于本地 —— 针对每次拉取动态数据需要时间。
  • 5s 的”挂起”状态 —— 进入后台后有 5 秒挂起状态，这种状态下 setData 没有必要执行。
  • 启用 Http2、Quic 协议 —— 与后台进行数据交互时可以启用 Http2、Quic 等协议。
  • getCurrentPages() 接口 —— 在 page.onUnload 中将定时器以及 wx.onXXX 的全局监听和与全局对象有关的事件监听全部移除。
  • 原生的 Context 节点 —— 原生组件可以通过 SelectorQuery 查询到原生节点，再利用这个节点直接操作和更新视图。
  • 本地图片上传到云。

3.3 骨架屏

  • 优缺点：『不能使首屏渲染加快』，但在白屏时给用户提供反馈，『减缓用户焦虑』等待的情绪。
  • 在 data 中默认设置 loading: true，数据加载完成后再设为 loading: false；页面里通过 wx:if 和 wx:else 切换，避免数据先加载出来与骨架屏页面『重叠』。
  • 不要直接修改生成的骨架屏代码。
    • 修改配置以后要重新生成骨架屏代码；wxml 或 js 代码后续有修改，也要重新生成骨架屏。
  • 骨架屏只给主页使用。

3.6 优化视图层动画效果

  • 使用 Animation 对象实现的 CSS 动画 —— 效率最低。
  • 使用页面或组件对象拥有的 animate 实现『关键帧』动画 —— 第一推荐，但效率不是最高。
  • 滚动事件驱动的响应式动画 —— 推荐的低成本创建响应式页面效果的方式。
    • 『本质上响应式动画也是通过 animation 接口实现的』。
    • 依据 scroller 组件的滚动而变化。
    • 通过 wx.createSelectorQuery().select('#id').fields() 查询 scroller 组件。
    • 然后在回调里调用 animate 设置它的对象，并在 onReady 中调用。
  • 通过 WXS 脚本实现的样式动画 —— 效率最高，适用于高频动画，但目前只支持 ES5。
    • 由 .wxs 脚本实现，事件绑定在一个 WXS 脚本导出的事件句柄函数上。
    • 通过『事件句柄函数的 ownerInstance』调用 selectAllComponents 或 selectComponent 查询页面上的组件，查询后通过 setStyle 设置组件样式。

3.7 重渲染与自定义组件优化

重渲染：使用新的节点树，有目标地将原节点树上需要更新的节点一一更新的过程。

  • 将界面功能组件化 —— 频繁改动的功能。
  • 去掉不必要的数据设置，减少每次 setData 设置的数据量。
  • 通过 WXS 脚本改写组件，把可以在视图层完成的代码逻辑下放到视图层。
    • wxml 中增加 WXS 模块的引入，并在 view 上添加 change:mode 与 mode 属性；WXS 脚本中通过函数判断 mode，调用对应模式的函数或代码：change:mode="{{ index.modeObserver }}" mode="{{ mode }}"。
    • 使用 page.requestAnimationFrame() 可以防止跟不上渲染造成卡顿。

3.13 使用异步转同步的编程范式

异步编程：除了主线程以外还有一个或多个异步线程，异步线程处理 worker、timer 定时器、网络请求、用户输入监听、事件派发等任务。『当异步线程有回调函数代码需要执行时，异步线程会将这些代码推入主线程的执行队列，由主线程在不忙碌时尽快执行。』

  • 编写异步转同步函数：用 promisify 替代 request，文件放在公共位置。
  • require 不支持绝对路径，但在 app.js 文件中可以使用绝对路径。
    • 全局的应用实例可以通过 getApp() 取到，app.js 位于项目根目录，便于标记。
    • 函数调用时为了避免程序报错，后面一定要加上默认的 catch。
    • 使用 promisify 函数的父函数添加了 async 关键字后已经是同步函数，要避免在主线程上以阻塞的方式调用，即『用 await 关键字调用函数』。

3.14 使用复合命令模式对齐代码的执行点

复合命令模式是一个设计模式，和异步转同步的编程范式一样，主要作用是让代码结构更清晰、易于维护，其次还可以优化代码的调用逻辑，统筹安排代码的执行时机。

  • 在 App.onLaunch 事件中开始拉取动态数据，把 App.onLaunch 和首页的 Page.onLoad 这两个时间节点用并发的复合命令模式管理起来，让它们可以并发执行。

3.15 使用 Worker 开启新线程进行耗时运算

Worker：依托宿主环境存在，可以在后台并行执行 JS 代码而不影响页面渲染。可以把 Worker 看作异步线程，在异步线程中执行比较耗时的计算，计算完成后再把结果同步给主线程使用。

  • 在 app.json 中配置 workers，声明 Worker 代码所在目录。
  • 创建组件，只有 js 需要改动，使用后要主动销毁 Worker：
  • Worker 和 WXS 都是异步执行，但 Worker 的限制更多：
    • 不能使用 wx 开头的小程序接口。
    • workers 目录下可以有很多 Worker 文件，但同一时间只能有一个 Worker 线程开启；要开新线程需要先停掉、销毁原来的线程，并且系统资源紧张时 Worker 线程还可能被系统回收。
    • Worker 只能放在特定的、已经配置好的目录下，不能随意放到其他目录。
    • 通讯不方便，Worker 线程和主线程之间只能通过 postMessage 和 onMessage 相互通讯，相当于观察者模式的一种通讯机制。

3.16 在后端使用 Go 语言异步执行逻辑运算（把前端工作后移）

  • 扩展接口时，把 Go 代码中要扩展的接口主要代码、相关变量和函数拷贝到项目中要使用页面的其他代码上方。

3.19 小程序切换后台后关闭 setData 调用

  • 用 wx.onAppHide 监听小程序进入后台事件，或者用 App.onHide 捕捉进入后台的时机。
  • 劫持 Page 对象：在 page.js 文件中先劫持 onLoad 和 setData，在 onLoad 中获得 setData 的引用，然后在 app.js 文件中调用 page.js。

  • 如果必须劫持，一定要把劫持代码统一放在程序的入口处。

  • 需要在微信小程序平台开启。
  • 使用并发复合命令的竞赛模式拉取数据：
    • wx.onBackgroundFetchData：微信拿到预拉取数据时设置的回调函数。
    • wx.getBackgroundFetchData：主动获取微信在本地缓存的预拉取数据，本地没有则拉取失败。

3.21 优化后端接口及网络请求参数（wx.request）

  • enableCache：开启 cache。
  • enableHttp2：开启 HTTP/2 —— 后端需要开启相关支持。
  • enableQuic：开启 QUIC —— 第三代网络协议，后端需要开启相关支持。

3.22 视图代码优化技巧

1. 动态列表渲染中的 wx:key

  • 如果列表元素是『单一』的基本数据类型，并且唯一，直接写成 *this，*this 代表当前数据列表中的元素 item。
  • 如果列表元素是『对象』类型，可以填写对象中的一个『字段名』，该字段名在整个数据列表中必须唯一。
  • 列表『不是动态』的、只渲染一次时，wx:key 设置为 index。

2. 绑定视图事件

  • 使用 catch 代替 bind，不需要冒泡、只在特定节点监听事件。
  • 回传额外信息用 data- 的形式。

3. 节流与防抖

  • 节流：控制某段 JS 代码的执行频率。
  • 防抖：避免一次事件被当作多次处理。
  • 对于 scroll 这类高频事件要节流，使用节流函数 throttle。
  • 对于用户的『单击』事件，可以适当使用防抖函数 debounce，防止按钮误单击。

4. 克制使用重渲染与 wxml 标签

  • 减少 wxml 节点数量：总页面节点数少于 1000 个，节点深度少于 30 层，子节点数不大于 60 个。
  • 控制 setData 每次传递的数据量。
  • 能不用容器标签就不用。

3.24 UI 交互技巧

  • 使用『padding 改变单击区域大小』。
  • 使用『伪元素改变点击区域大小』：给父元素 position: relative，伪元素设为 absolute，并把 top、left、right、bottom 设为负值来扩大点击区域。

3.25 脚本优化技巧

  • 如果对象被异步线程引用，或者被全局对象引用，会造成内存泄漏。
  • 定时器属于异步线程，离开页面一定要记得销毁。
  • 『使用 wx.onXXX 全局绑定一定要小心，有一个监听必须有一个反监听，在 onUnload 事件中销毁』。
  • 主题切换事件可以在模拟器中通过在 app.json 配置 "darkmode": true 验证。
  • 使用全局对象要小心：
    • 所有在 global 上或 app 上定义的全局数据，以及在上面添加的事件监听，都要及时清理；自定义对象要定义一个 dispose 方法。
  • 使用 this 对象要谨慎，尤其是在周期性发生的异步回调函数里。

3.26 setData 调用优化

  • 小程序切换到后台后，setData 不再调用，可以结合小程序的双线程运行机制和重渲染机制理解。
  • 不要多次分开调用 setData，尽量合并调用。
  • 不准备渲染的数据不要放在 data 数据对象里。
    • 『只有需要触发视图更新的数据才需要放在 data 对象』。
    • 不需要触发的，可以放在 data 对象外面（即当前页面对象上），通过 this 直接取用。
  • 通过 index 局部更新长列表数据：
    • 使用索引或计算属性更新局部数据。
    • 直接使用当前组件上下文对象的 update 方法。

3.27 网络请求优化：本地缓存与请求优先级

1. 用本地缓存减少不必要的请求

首页 JS 文件里有加载小程序导航数据的代码，可以在这里尝试本地缓存：先从本地缓存中取数据展示，然后向后端发起请求，拿到最新导航数据后再调用 setData 重新设置，并把本地缓存刷新一遍，避免缓存过时（优化：改用并发复合命令或两个异步函数）。

踩坑与注意点

  • 骨架屏不会加快首屏：它的价值是减少白屏焦虑；且不要在生成结果上手动改代码，配置或 wxml/js 改动后要重新生成。
  • setData 有硬限制：单次数据不超过 256KB；页面节点总数控制在 1000 以内、层级少于 30 层、子节点不多于 60 个。
  • 离开页面要清理：定时器、wx.onXXX 全局监听、挂在 global/app 上的数据和监听都要在 onUnload 等时机移除，否则会内存泄漏。
  • WXS 只支持 ES5：在 WXS 里写 ES6 语法会直接报错。
  • Worker 不能调 wx 接口，且同一时间只能有一个 Worker 线程，位置也必须在配置好的目录中。
  • require 的路径限制：require 不支持绝对路径，只有 app.js 中可以使用绝对路径，因此才需要额外封装 requireAsync。
  • 带 Sync 的接口仍是同步的：如 wx.getStorage、wx.setStorage、wx.getSystemInfo，放在 onLaunch / onLoad 中会阻塞启动，尽量后移到 onReady 之后或用拆分接口。
