小程序登录的主线是：先定义 token 容器和 token 管理器 → 封装统一请求 → 在请求层之上封装 API → 用 wx.login() 拿 code 换取业务登录态 → 用一个 Promise 缓存登录过程，避免每个页面都重复发起静默登录。结论放在前面：静默登录必须做「单例」，否则全局组件和页面同时触发时会并发请求；token 既保存在内存（供请求头使用），也要序列化进缓存（供下次启动判断是否已登录）。

场景

小程序启动即静默登录，token 由后端在登录时生成返回。前端需要把 token 存好、带在每次请求上，并处理「首次启动、token 过期、无需登录的接口」这几种情况。

因为静默登录每个页面都会触发，所以用第 5 步的登录状态变量做一次缓存：已经发起过就把同一个 Promise 返回出去，失败后再重置，允许下一次重试：

如果全局只调用一次，可以在设置完 token 后用 wx.setStorageSync() 存进缓存，之后根据 token 是否存在判断是否需要重新登录。

8. 在全局组件中调用

把静默登录这个方法放到全局组件中调用，保证每个页面进入时都有登录态可用。

优化

判断 Promise 的登录状态（并行请求，先获取先展示）

  1. 在全局封装一个登录状态，调用时如果没有登录状态，就把静态登录的状态赋值给它。
  2. 然后 await 等待成功才继续执行下面的语句，没有成功不执行，最后完成重置状态。

重复登录问题

  1. 统一在登录逻辑那里处理。
  2. 在默认登录时设置登录后缓存，缓存数据最好使用序列化，把类型变为 string。
  3. 写一个函数用来判断是否已登录：获取缓存，判断有缓存就把数据反序列化后重新设置 token 并返回 true。
  4. 完成后在整个登录逻辑那里调用该函数，判断是否为 true，是则返回。

登录校验问题

  1. 在不需要登录的路径上传参数 cross，然后到请求页面中返回时从路径拿到 cross。
  2. 有 cross 时需要与之前的 data 合并。
  3. 之后在请求方法中判断：不存在 cross 就走原先的静默登录状态判断，存在则直接请求并返回结果。

解决路径调用 API 时无提示、不报错问题

  1. 在全局中使用函数和简单索引类型。
  2. 通过泛型让 K 遍历 T 中的每一项，返回 T 时拿到 K。
  3. 使用时就有提示。

注意

  • _to 是「把 Promise 转成 [err, res]」的工具函数。
