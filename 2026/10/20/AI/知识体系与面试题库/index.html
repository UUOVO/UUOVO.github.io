二、AI 应用基础

2.1 核心概念

  • 训练：需要大量数据，且必须是领域数据。
  • 模型：用海量数据训练出来的产物。
  • Prompt 优化：决定输出质量的关键可变项。
  • 输出：最终交付给用户或下游系统的结果。
  • 知行合一：概念要能落到工程实现，才算真正掌握。

2.2 模型应用发展的三个阶段

阶段 含义 前端关注点
Prompt 用户输入提示词，模型按要求生成 提示词交互设计、参数暴露
RAG 外挂知识库辅助模型输出，结果更贴合期望 知识库管理界面、引用溯源
Agent 智能体，能编排「内容加工 → 输出」的完整流程 过程可视化、人机干预

2.3 LLM 基础

大语言模型是基于海量文本训练、拥有数千亿甚至万亿参数的深度神经网络。核心机制：给定上下文，预测下一个最可能的 token，不断预测即可生成连贯文本。

  • 核心能力：概率预测。
  • 关键特性：
    • 涌现能力：规模达到阈值后表现出未被明确训练过的复杂能力。
    • 上下文依赖：回答质量完全取决于提供的上下文。

基础模型（Foundation Models）

  • 定义：通用领域海量数据预训练，具备广泛知识与多种能力，是所有垂类应用的「毛坯房」。
  • 例子：GPT-4、GPT-3.5、Claude 3 Opus、Gemini 系列、Llama 系列。
  • 场景：项目初期快速验证，或需要广泛知识、强推理与生成能力的场景。

微调模型（Fine-tuned Models）

  • 定义：在基础模型上用特定领域、高质量、小规模数据集做额外训练，使其在特定任务或风格上表现更优。
  • 场景：医疗文献、公司内部代码库等。

选型必须关注的三个差异点

  • 上下文窗口：能处理的最大长度；过长也可能「大海捞针」。
  • 成本：按 token 计费，输入输出价格不同，应避免携带不必要的长对话历史。
  • 响应速度：不同模型推理速度差异很大，直接影响体验。

2.4 提示词工程四招

技巧 作用
角色扮演（Role-playing） 开头设定角色再带入问题，提高特定领域回答质量
思维链（Chain-of-Thought） 指令「分步思考」，提升数学、逻辑、复杂规划的准确率
结构化输出（Structured Output） 强制返回 JSON，免去字符串解析，直接用于数据绑定与状态管理——前端最实用的一招
指令与数据分离 用明确分隔符把指令与待处理数据隔开，减少模型混淆

2.6 流式输出（SSE）与打字机效果

SSE（Server-Sent Events）：即 EventSource，服务端自有推送能力，允许在一次 HTTP 连接中持续向前端发送 text/event-stream 格式数据，无需客户端反复轮询。

打字机效果的完整链路：

  1. 客户端请求时将 responseType 设为 stream。
  2. 服务端用 SSE 实现流式响应，关键在响应头：
    • Content-Type: text/event-stream
    • Cache-Control: no-cache
    • Connection: keep-alive
  3. 数据通过遍历逐块下发；客户端设置 UTF-8 编码，用 while 循环解码并拼接。
  4. 拼接结果实时追加渲染到页面。
  5. 接入 AI：把模型返回的增量数据写入服务端响应流，即得到 AI 打字机效果。

典型架构（自然语言 → 图表）：LLM + Text2SQL + DSL

3.4 AI 应用引擎的六大核心模块

生成式 AI 应用引擎 = 在传统工作流基础上，集成大模型、智能体搭建、插件、工作流、触发器与辅助功能的综合平台。

模块 职责
插件（Plugins） 通过插件化机制把复用的处理逻辑抽象出来，扩展模型能力、对接外部系统。每个插件实现统一接口，可在不同模块中被调用
工作流（Workflows） 一系列可执行任务的自动化流程；每个任务封装为一个「节点」，按顺序（或图关系）执行
触发器（Triggers） 根据用户输入或系统状态自动触发某些操作；前端可依据用户行为、系统状态触发工作流或插件
知识库（Knowledge Base） 存储并管理知识，使引擎能针对不同查询给出准确答案
记忆（Memory） 保持与用户的历史交互与上下文，使响应更个性化、更有上下文相关性
用户输入 / 输出 前端收集信息并向引擎发起请求，引擎返回结果

Coze 核心业务视角（五件事）：人设（Prompt）、技能（插件化思维创建插件）、知识库、工作流、发布机制（发布到不同渠道，或作为插件插入网页）。

重难点五件事：① 流程编排引擎编辑器 ② 流程节点执行沙箱 ③ 日志系统 ④ 错误处理机制 ⑤ 服务化。

3.5 实操：私有化部署一套 AI 应用引擎

前置检查：CPU 至少 2 核、内存 4G 以上，安装 Docker。

方案 A：Coze Studio（开源版）

  1. 从 https://github.com/coze-dev/coze-studio 拉取源码。
  2. 按 README 用 Docker Compose 部署。
  3. 配置模型对接（如火山豆包模型的 API Key 与 Endpoint）。

方案 B：Ollama + Dify（本地模型 + 知识库）

  1. 安装 Ollama 与 deepseek-r1:latest、Docker。
  2. 模型：deepseek-r1:latest 残血版，通过 Ollama 部署。
  3. 知识库：Dify 向量数据库，Docker 部署。
    • 下载 GitHub zip，解压后在 docker 目录执行 cp .env.example .env 与 docker compose up -d
    • 检查容器是否齐全
    • 浏览器访问 localhost；初次安装访问 localhost/install，配置邮箱、密码、管理员账户
  4. 在 Dify 引入模型：设置 → 模型供应商 → Ollama → 添加模型，配置名称（deepseek-r1:latest）、URL（http://IP:11434），其余默认。
    • ⚠️ 容器化场景下 URL 不能写 localhost，必须写宿主机局域网 IP。
  5. 创建空白应用（对话 / 工作流编排），建知识库，按步骤发布；他人可通过 API（有文档）或网页版访问；智能体发布后相当于进了应用商城。

价值点（面试可直接用）：不仅能说清部署流程，还能从平台构建者视角说明一个 Agent 如何通过人设、插件、知识库（RAG）、工作流几大模块协作，从简单问答走到复杂业务流程自动化。

四、RAG 与 Agent 原理

4.1 RAG 全链路（前端视角拆解）

核心价值：给大模型外挂一个「实时、私有的知识大脑」。

阶段一：数据准备与索引（离线 / 后台）

  1. 文档加载（Loading）：从各种源加载原始文档。
  2. 文本切片（Splitting / Chunking）：长文档切成有意义的小块。常见策略：固定长度切块、按段落/标题切块、递归切片。
  3. 向量化（Embedding）：调用 Embedding 模型，把每个文本块转成高维向量——即该文本块在「语义空间」中的坐标。
  4. 入库（Storing）：将文本块原文与对应向量一并存入向量数据库。

阶段二：查询与生成（在线 / 实时）

  1. 用户提问：前端接收问题。
  2. 问题向量化：用与索引阶段相同的 Embedding 模型把问题转成向量。
  3. 向量检索（Retrieval）：在向量库中搜索语义最相似的文本块向量。
  4. 上下文增强（Augmentation）：把 Top-K（如最相关的 3 个）文本块与用户原问题组合成一个信息量更大的 Prompt。
  5. 生成答案（Generation）：把增强后的 Prompt 发给 LLM，基于给定材料生成最终答案。
  6. 前端呈现：
    • 流式输出（Streaming）：逐字渲染答案。
    • 引用溯源（Citation）：RAG 应用的黄金标准。界面必须清晰展示答案的每一部分基于哪个检索到的文档块——既建立信任，也提供深挖入口。

4.2 Agent 与 ReAct 循环

核心思想：自主循环。

Agent 本质公式

$Agent = LLM（大模型） + Planning（规划） + Memory（上下文记忆 / 持久化记忆） + Tool（工具） + User（MCP + Skills）$

ReAct（Reasoning and Acting）：目前系统级智能体最主流的推理框架，要求 LLM 在每一步都产出特定结构。

环节 说明
Thought（思想） LLM 自我反思：目标是什么？已知什么？下一步做什么？需要什么工具？该过程对用户不可见，但在后台日志中至关重要
Action（行动） 基于思考决定调用某个工具并给出输入，格式通常结构化，如 { "tool": "weather_api", "tool_input": "北京" }
Observation（观察） 系统真正执行该行动（如调用天气 API），把返回结果（如「北京今天晴，25℃」）作为观察再次输入 LLM
循环 接收观察结果后开始新一轮「思想 → 行动 → 观察」，直到认为目标达成，输出最终答案

核心价值：把 LLM 从「只会生成文本的模型」变成「能基于目标自主决策、调用工具、处理反馈的智能系统」。

4.3 工具（Tool）：智能体的手脚

本质：把 LLM 的文本生成能力映射为具体的函数、API、系统指令执行能力。

标准工具定义三要素

  1. 名称（Name）：唯一标识。
  2. 描述（Description）：说明这个工具做什么、什么时候用——这是 LLM 决策的关键依据。
  3. 参数（Args Schema）：输入参数定义，通常用 JSON Schema 描述。

常见工具类型

  • 搜索引擎 API：查询实时信息。
  • 计算器：精确数学运算。
  • 代码解释器：执行 Python，做数据分析或绘图。
  • 企业内部 API：查订单、取用户信息、操作 CRM。
  • RAG 本身也是一个工具：从私有库检索资料。

两个前端强相关点

  • 过程可视化：Agent 执行是动态、多步骤的，优秀前端应实时清晰展示当前状态——对调试、监控、建立信任都至关重要。
  • 交互式干预：允许用户在 Agent 执行过程中介入、修正方向。

4.4 智能体三分类与选型决策

① 工作流型智能体（DAG 有向无环图）

  • 核心本质：流程优先的确定性智能体。
  • 底层逻辑：人定义规则，AI 填充执行。
  • 代表产品：Coze、Dify、Make、n8n。

② 通用型智能体（完全依赖 LLM Planning）

  • 核心本质：目标优先的全自主智能体。
  • 底层逻辑：人定义目标，AI 定义规则与执行。
  • 代表产品：Manus、openManus、AutoGPT、GPT-4o。

③ 垂类智能体（深度定制）

  • 三个特征：领域知识深度融合、专用工具极致封装、场景化交互深度适配。
  • 核心本质：场景优先的专用型智能体。
  • 底层逻辑：场景定义规则，领域知识赋能，AI 在边界内精准执行。
  • 代表产品：剪映智能剪辑、Figma AI、GitHub Copilot、阿里云智能客服、墨问 AI。

选型决策树

4.5 前端视角的智能体四阶闭环

  1. 感知层：智能体的「眼睛和耳朵」，采集用户输入、系统环境状态、外部数据反馈——对应前端的事件监听、数据订阅、环境状态采集，是前端的传统优势阵地。
  2. 决策层：智能体的「大脑」，基于 LLM 内核，结合感知输入与记忆上下文，完成任务拆解、步骤规划、工具选择、异常处理——前端负责决策逻辑封装、Prompt 编排、边界校验规则。
  3. 行动层：智能体的「手脚」，执行指令：调用 API、操作文件、执行代码、控制系统指令——对应前端工具封装、接口调用、Node 脚本执行、系统 API 适配，是全栈能力的核心体现。
  4. 记忆层：智能体的「知识库」，存储会话上下文、执行历史、用户偏好、领域知识——对应前端状态管理、本地持久化、向量库交互，决定长程任务能力。

4.6 长链条任务的三个硬难点

  1. 任务拆解策略与边界判定：三种智能体在 Prompt 工程与工具链调用上的本质区别。
  2. 长链条 ReAct 的自修复循环与跨进程通信
    • 用 LangGraph 实现具备「状态机」属性的复杂 Agent 逻辑。
    • 难点：设计健壮的 Commander 系统指令集封装层，把 AI 的模糊意图精准翻译成操作系统可执行的原子指令（CLI / API）。
    • 重点：长链条任务中环境保存 / 变更时，如何通过 Error-Reflexion（错误反射） 实现自动纠错与路径重规划，避免死循环。
  3. 多 Agent 协作协议的复杂业务闭环
    • 类似 openclaw 系统级架构，核心是 Multi-Agent 协同中的通讯协议（SOP）与资源竞争管理。
    • 企业落地：私有化知识库（RAG）与实时工具调用（Function Calling）的深度融合策略，解决大规模并发下的幻觉控制。

五、AI 应用开发框架

5.1 直接调模型会遇到什么（为什么要框架）

模型只具备「分析与推测」能力，Agent Loop 则是不断调用工具拿结果、再从结果学习优化的反复过程。直接开发会撞上七个问题：

  1. 多模型接入需要适配器（Model Provider）——微内核设计思想，用统一标准化协议完成模型接入。
  2. 工具定义与调用机制（tool calling）。
  3. 循环：ReAct 框架。
  4. 模型输出形态：字符串、流式。
  5. 调用远程他人的 tool 需要一套标准化规则，即 MCP。
  6. 大量提示词优化：上下文压缩（compact）、Skills（元数据 + 可执行操作）。
  7. 生态适配。

LangChain.js 对以上都做了封装，所以选它。

小 Demo 技术栈

  • TypeScript（类型完备）+ Node.js 经验：脚本测试 → 服务化（Express、Koa、Next.js、Nuxt.js、NestJS）。
  • 本地模型部署：Ollama、MStudio、Whisper。
  • AI 引擎：LangChain.js、LangGraph.js、DeepAgent.js、Mastra、RAGFlow……
  • 方法论：问题分析 → 方案设计（MVP，抓住主要矛盾）。

5.2 LangChain 标准化接口：如何避免供应商锁定

LangChain 通过 BaseLLM / ChatModel 等核心抽象定义标准化模型接口，抹平了 Ollama（@langchain/ollama）、OpenAI、云厂商模型在调用协议、参数格式、返回结构上的差异。

  • 现在用本地 Ollama，将来切云端大模型，只需替换模型实例化逻辑（OllamaChatModel → ChatOpenAI），无需改动提示工程、工具调用（d3-dsv 解析、pg 交互）、Agent 编排等核心业务代码。
  • 标准化接口还统一了错误处理、上下文管理、流式输出等通用逻辑。
  • 结果：降低切换成本，并支持多供应商混合调用（核心场景用云端、低成本场景用本地），规避单一供应商的定价、稳定性、合规风险。

5.3 LangChain 与 LangGraph 的选型

选型锚定业务复杂度与流程特性：

场景 选择 理由
轻量：线性流程、单轮简单多轮交互（基于 pg 数据的问答、d3-dsv 解析结果返回） LangChain 核心套件 AgentExecutor、PromptTemplate 等开箱即用，开发效率高，适配中小规模、无复杂状态管理的业务
复杂：非线性流程、多角色协作、状态持久化 / 容错重试（「拆分 → 入库 → 推理 → 纠错」闭环） LangGraph 基于 LangChain 核心扩展，主打「有状态的推理图」，支持节点拆分、条件分支、循环执行，能精准描述状态流转，且可嵌套复用 LangChain 的工具与提示组件

5.4 可解耦、可演进的 Agent 分层架构

按 接口层 → 原子能力层 → 编排层 → 业务层 分层，每层职责单一、依赖倒置：

  1. 接口层：封装统一的模型调用（基于 @langchain/core 抽象）与工具调用接口，屏蔽底层差异（pg 数据库、d3-dsv 解析均封装为标准 Tool）。
  2. 原子能力层：拆分提示模板、文本拆分、数据解析、数据库交互等原子能力，用 Zod 做参数校验，确保可复用、可独立迭代。
  3. 编排层：轻量场景用 LangChain AgentExecutor，复杂场景用 LangGraph 构建状态图；只负责流程编排，不耦合具体业务逻辑。
  4. 业务层：对接 Express 接口、业务规则等具体场景，通过配置化关联编排层与核心能力；新增业务只扩展这一层，无需改动底层。

5.5 LangGraph 专家级内核（对标自研的六要素）

LangGraph 作为工业级 Agent 框架，核心竞争力在于一套完整的「图执行 + 状态管理」体系：

  1. 状态机驱动：基于有限状态机（FSM）与有向无环图（DAG），保障执行的确定性与可追溯性。
  2. 图执行引擎：支持节点的顺序、分支、并发、嵌套组合。
  3. 异步安全与竞态避免：确保多异步任务执行时状态一致，无脏数据覆盖。
  4. 状态持久化与 Checkpoint：执行快照、断点续跑、跨实例恢复，适配长周期任务。
  5. 子图与嵌套图：复杂流程拆为子图，提升复用性与可读性。
  6. 执行监控与调试：完整执行轨迹、日志与状态回溯，降低排障成本。

前置知识：图论的基本概念——节点与边、有向图。

六、工作流与 AI 应用引擎架构

本章是全篇的架构核心：所有「AI 应用平台 / 低代码 / 扣子类产品」的骨架，都是编辑器 + 执行器 + 协议。

6.1 三种平台形态

形态 实现方式 示例

低代码平台 借助工作流编排，涉及触发器、代码执行器、数据查询器、循环节点等 Retool

  • 低代码：retool
  • AI 应用生成引擎：coze
  • 本地部署：Dify（见 §3.5）

流程引擎的本质：自动化管理和执行既定的业务流程，涵盖自动化处理、批处理、AI 生成详细过程。
三大核心功能：

  1. 工作流流程建模（编辑器）
  2. 任务调度：异步处理、前后依赖、变量上下文
  3. 集成外部系统、插件化构建流程功能生态

6.2 常见工作流类型

  • 线性流（Sequential）：最简单的逻辑，节点按 A → B → C 顺序执行。
  • 有向无环图（DAG）：AI Agent 最常见的形态，允许分支与回合，但严禁形成环路（会死循环）。
  • 状态机驱动流（State Machine）：侧重状态流转（审批通过、驳回、待补件），每个节点是一个状态，连线即触发动作。

6.3 节点体系

核心节点

节点 作用 配置要点
start 节点 工作流起点，由外部事件或用户输入触发 字段类型（文本/段落/下拉/数字）、变量名称、显示名称、最大长度、是否必填
模型节点 调用生成式 AI 模型做生成或理解 选择模型与参数（温度、Top P、存在惩罚、频率惩罚、最大标记、回复格式、停止序列）、上下文、提示词、记忆（记忆窗口）、输出变量
知识检索节点（可选） 检索已有知识库 查询变量（自动带入 start 变量）、知识库（选一篇或一个文件夹）、输出变量
条件节点 分支控制 if 区域可加多个条件；else 区域直接显示描述词
代码执行节点 自定义逻辑 输入变量（初始两个「名 / 值」，可增删改）、代码编辑器（可直接使用输入变量）、输出变量（变量名 + 类型）

扩展节点类型（平台生态视角）

  • 插件节点：调用外部插件完成集成型任务（天气查询、支付处理）。
  • 业务逻辑节点：执行条件判断或复杂算法（如选择支付时触发支付流程）。
  • 子工作流节点：把一个工作流嵌套进另一个工作流，支持递归调用，提升可重用性。
  • 结束节点：所有任务执行完毕，返回最终结果。

交互细节：每个节点连接下一节点时，右键可拿到当前节点可连接的所有节点（即类型校验后的候选集）。

6.4 数据协议与 DSL

两大构成要素

  • 节点（Node）：定义功能。
  • 边（Edge）：定义来源（from / source）与目的（to / target），约束节点关系与流程。

DSL（Domain Specific Language） 领域特定语言，可与 AST（Abstract Syntax Tree） 结合使用。

假设有三个节点：触发器 trigger、新建标签页 newTab、滚动执行器 scroll，从左往右连接成有向无环图。

协议设计四要求：数据兜底、降级、扩展、升级。

  1. 数据结构定义 → 引擎数据协议设计（兜底、降级、拓展、升级）。
  2. 引擎实现：Canvas、SVG、自研框架 三选一。
  3. 节点 / 边定义与灵活拓展 → 物料体系灵活接入，基于插件化 / 微内核机制（可对接远程插件市场、MCP）。
  4. 编辑器协同 + 执行引擎实现：协同用 CRDT / OT 解决冲突；执行要处理建图、遍历、异步、日志、错误收集。

6.6 执行器：内存型 vs 服务型

维度 内存型工作流（In-memory） 服务型工作流（Service-based）
执行环境 浏览器端或单个 Node.js 进程内存 分布式微服务集群
状态存储 随进程结束释放，瞬时性 数据库持久化（MySQL / Redis），支持断点续传
适用场景 前端低代码预览、轻量 AI 助手、单纯数据转换 复杂审批流（需人工参与）、长时耗任务、支付链路
核心挑战 内存溢出与性能：节点过多导致浏览器卡死 幂等性与重试：节点执行一半服务宕机如何恢复

内存型执行机制

  • 顶层设计：典型的事件驱动模型。
  • 运行逻辑：引擎把整个 Graph 加载进内存，通过递归或循环消费任务队列。
  • 关键点：快照同步（每行执行完直接更新 UI 状态）、轻量化（无需考虑网络延迟，节点间数据传递用引用或简单 Copy）。

服务型执行机制

  • 顶层设计：任务队列 + 状态机持久化（类似 Temporal、Camunda 的简化版）。
  • 运行逻辑：
    1. 任务解耦：引擎把待执行节点推入消息队列（RabbitMQ / Redis）。
    2. Worker 消费：不同 Worker 认领任务并执行，结果写回数据库。
    3. 状态脱水与复活：需要「人工审批」的节点，引擎把流程挂起（Wait），上下文脱水（Serialize）入库，触发后再复活（Hydrate）。
  • 关键点：必须处理分布式事务与超时重试。

6.7 执行器实现：从最小闭环到生产可用

① 最小实现（内存型）

编辑器 + 执行器都在前端时，三步走：

  1. 约定流程协议（节点与边的 JSON 数据）。
  2. 编辑器编排工作流数据。
  3. 开发执行器：从前到后按序执行，后面的节点可以拿到前面节点的上下文，通过链表串联。

② 生产级三项增强

1）完全稳定可靠的日志系统（基于异步实现）
在每个节点执行前后记录：节点开始时间、输入与输出数据（敏感数据需加密或遮盖）、执行状态（成功 / 失败）、错误信息。

2）上下文变量池

  • 在整个流程执行期间保持全局有效，存储所有必要的状态信息。
  • 内容包括输入数据、计算结果、外部调用响应等。
  • 每个节点执行时，执行器按需从池中取数据或更新数据。

3）错误处理机制

  • 全局错误捕获：兜住所有未处理错误并记录相关信息。
  • 节点级错误处理：每个节点可定义自己的错误策略，如 API 报错重试。
  • 错误通知：关键节点出错时通知管理员或用户。
  • 错误恢复：可恢复错误（如网络请求）设计重试机制。

6.9 前端编排 + 后端执行的关键难点

前端编排引擎：本质是一个面向 AI 工作流的、可视化的 DAG 编辑器。

  1. 状态管理与交互：用户拖拽节点（工具、LLM、判断逻辑）并连线，实时构建复杂图结构。需要强大的状态管理方案（Redux Toolkit、Zustand）维护完整数据结构——每个节点的位置、配置与连接关系。
  2. 图结构序列化：点击「调试」或「发布」时，前端必须把可视化图序列化成后端执行引擎能理解的标准 JSON，描述拓扑结构与每个节点的具体参数。
  3. 实时调试反馈：调试模式下后端逐节点执行时，前端要实时高亮当前节点并显示输入输出。这要求前后端建立长连接（WebSocket 或 SSE），由后端主动推送执行状态与日志。

后端流式节点执行引擎：整个架构的「技术之巅」。用 for 循环按序执行是天真实现，低效且无法处理流式输出。工业级引擎必须解决：

  1. DAG 解析与执行调度：拿到工作流 JSON 后先做拓扑排序，确定执行顺序，并识别可并行执行的分支。
  2. 异步非阻塞 I/O：几乎所有节点（调 LLM、调 API、查数据库）都是 I/O 密集型，引擎必须完全异步非阻塞（Node.js 事件循环，或 Go 协程）。
  3. 流式处理（Streaming）：LLM 节点不能等全部生成完再返回。
    • 调用大模型时明确要求流式返回（如 OpenAI API 的 stream: true）。
    • 引擎收到的是数据流而非完整响应。
    • 通过 WebSocket / SSE 把每个数据块（token）实时转发给前端，实现打字机效果。
    • 同时把数据块拼接成完整输出，作为下一节点的输入。
  4. 安全沙箱（Sandbox）：执行社区开发者贡献的代码片段或插件时，绝不能在主服务直接运行。
    • 方案一（重隔离）：为每个任务动态启动轻量 Docker 容器，隔离最好但冷启动慢。
    • 方案二（轻隔离）：WebAssembly（WASM），启动极快、安全性高，是很有前景的方向。

工程化闭环五步：① 定义 DSL → ② 编辑层（状态管理 + 插件化架构）→ ③ 执行器（拓扑排序与动态调度、沙箱隔离）→ ④ AI 特化设计（变量提取与上下文流转、流式输出）→ ⑤ 测试与工程化闭环。

6.10 沙箱的两层理解

  • 记忆方式： 通过费曼学习法，记住一个，根据另一个进行推导。
  • 微前端沙箱（如 qiankun 的三种 sandbox）：legacy sandbox、proxy sandbox、snapshot sandbox，目的在样式隔离、JS 隔离。
  • 系统级沙箱：目的是系统环境隔离，保证执行安全性。deepagent 涉及文件操作、bash 执行、shell 提权，必须做隔离。
  • 服务端隔离强度排序：Docker 容器（强隔离、冷启动慢）→ WASM（轻隔离、启动快）→ vm2 / isolated-vm（进程内隔离，性能好但需谨慎使用）。

② 路线一：浏览器 execCommand（小白级，过时 / 即将废弃）

  • document.execCommand 是浏览器 API，用于在 HTML 文档中执行与内容相关的命令。
  • 缺点：兼容性差、可维护性差。

③ 路线二：Selection + Range + Compiler（大神级）

  • 单独用 selection（获取当前选中内容）+ range（精确操作选中内容）时会发现：每点击一下就被新的标签包裹。Compiler 负责切换——判断当前内容是否已有修饰标签，是则还原，否则添加修饰。

    1. 基于 Markdown：性能更好、约束更强。
    2. 基于 JSONContent：特性更灵活，自定义节点更便捷（如 TipTap custom node）。
  • 内容 → 可存储格式 → 再解析回来：实现 JSON 与 HTML 双向转换，可参考 html2json。
    • HTML 转 JSON：递归遍历 DOM 元素，构建结构化 JSON。
    • JSON 转 HTML：从 JSON 数据生成 HTML 字符串，支持富文本格式。

8.3 为什么 AI 产品首选 SSR

AI 产品的特殊性

  • 追求短平快（全栈）：一套框架同时解决页面与接口。
  • 隐私和安全：
    • 数据以 JSON 请求暴露在浏览器，只要拿到 token，就能在任何位置频繁调用你的接口。
    • 很多第三方服务（OpenAI 等）的 token 若放前端会直接泄露。
  • 动态响应与个性化：需要按用户、按会话动态生成内容。

SSR 的三点优势

  • 用户体验（首屏更快）
  • 减轻客户端压力
  • 降低维护成本

典型的 AI 项目形态：Dify、Coze 类 AI 应用开发平台（Prompt、RAG、知识库、模型部署与接入、流程编排、function calling、MCP 接入，以及企业级模型调优 / 数据集 / 训练）；v0、bolt 等 AI 生成类产品。

8.4 Next.js 实战

① 创建项目

  • 关注路由：早期主要用 Pages Router，现在用 App Router。App Router 支持模块化、组件化，并在预渲染、服务端优先水合、布局与路由的服务端优先上做了架构优化。
  • 创建过程中：TS、ESLint、App Router、Turbopack 必选；TailwindCSS、src/ 目录、路径别名按需。
  • 约定式路由：按文件目录结构创建文件，浏览器输入对应 URL 即可进入，无需配置 router。如在 home 文件夹下放 page.tsx，访问 localhost:3000/home 即可。

② 请求流程（五步）

  1. 用户请求页面，Next.js 处理请求。
  2. 服务端渲染：根据请求渲染出 HTML（getServerSideProps 获取动态数据）。
  3. 返回 HTML：用户看到浏览器初步渲染结果。
  4. React 水合（Hydration）：React 在客户端接管已渲染的 HTML，把静态 HTML 转为动态应用。
  5. 前端渲染：页面变为完整的 React 应用，用户可交互，React 接管后续界面更新与数据处理。

③ App Router 的关键约束

  • 新的架构下 Server Component 优先：React Hook 只能用在客户端组件，不能用在服务端组件。
  • 客户端组件：文件顶部加 "use client"。
  • 服务端组件：默认即是。

④ 动态路由

访问 localhost:3000/user 或 localhost:3000/user/1。

⑤ 编写 API

在 app 目录下创建 api 文件夹，文件名用 route.ts。

Pages Router 的写法是 export default function handler(req, res)；App Router 改为按 HTTP 方法导出具名函数。

9.3 全链路架构

话术（面试可直接背）

我主导并落地了一套端到端的全链路监控平台，覆盖从前端 SDK 无感采集（性能、异常、用户行为三类指标）、高吞吐消息队列缓冲、流式计算清洗，直到 OLAP 数据库（ClickHouse）落库与可视化的完整数据生命周期。

五段链路

  1. 端侧采集：自研埋点 SDK，sendBeacon + XHR 分级上报。
  2. 接入与缓冲：Nginx 负载均衡 → Node.js 网关 → Kafka 削峰填谷。
  3. 流式计算：Flink / Spark 实时清洗与聚合。
  4. 存储引擎：ClickHouse 列式存储，海量数据毫秒级查询。
  5. 数据应用：实时大屏 + 智能预警 + AI 根因分析。

接入层：高可用网关

  • Nginx：反向代理与负载均衡，承载海量并发，做 SSL 卸载与初步流量清洗。
  • Node.js（NestJS）：BFF / 接入服务，负责鉴权、数据格式校验，然后迅速把数据「甩」给 Kafka，不做耗时逻辑，保证接口 ms 级响应。

缓冲层：Kafka

架构决策：引入 Kafka 是为了解耦「生产」与「消费」的速度不匹配，实现流量削峰。

  • Topic 设计：按数据热度与结构拆分，如 topic_error_log（低频、高价值）、topic_performance（高频、海量）。
  • Partition 策略：按 session_id 或 user_id 做 Hash 分区，保证同一用户行为落在同一分区，从而保证时序性。

9.4 存储层：ClickHouse

为什么是 ClickHouse：监控数据具有「写多读少、按时间查询、海量数据聚合」的特征。

  • 写入性能：支持高吞吐批量写入。
  • 查询性能：列式存储 + 向量化执行引擎，亿级数据聚合（Group By）秒级完成。
  • 数据压缩：极高压缩比，节省大量存储成本。

写入优化铁律：千万不要单条插入。在 Consumer 层维护内存 Buffer，满足「数量达到 5000 条」或「时间间隔达到 5 秒」任一条件即批量 INSERT，最大限度减少 IO 开销。

十、工程化与架构

10.1 Monorepo：定义与四个核心特点

Monorepo（Monolithic Repository，单一代码仓库）

  • 一种软件开发架构策略。
  • 核心逻辑：把多个项目（Projects）、多个软件包（Packages）和公共组件库，全部放在同一个 Git 仓库中统一管理。
  • 通俗说法：前端、后端、服务端、自定义工具插件都在同一个文件夹下，通过 pnpm-workspace.yaml 定义 packages，彼此可互相安装、独立运行，但只提交一个 Git 仓库。
特点 深度解读
单一仓库（One Repo） 所有代码资产在一个 Git 历史中，一次 git clone 拿到组织工程全貌
多项目共存（Multi-Project） 仓库内用文件夹隔离不同业务应用与基础设施
统一依赖管理（Shared Dependencies） 所有项目共用一套基础依赖（React、TS、Jest），升级时同步升级，避免版本割裂
原子化提交（Atomic Commits） 一个需求同时改「后端 API」和「前端调用」时，可在同一个 commit 中提交，保证逻辑完整

Monorepo 解决的四个痛点

  • 代码复用性瓶颈 → 增强复用
  • 依赖管理复杂化 → 更友好的依赖管理
  • 跨项目原子性缺失 → 保证代码审查、持续集成与发布的一致性
  • 工程规范分散化 → 团队规范化、流程化、自动化

10.2 Polyrepo vs Monorepo

以「repo-frontend 需要 repo-utils」为例，Polyrepo 的做法是：改 repo-utils 代码 → 发布 npm 包（npm publish）→ repo-frontend 执行 npm i 安装。有 bug 就重复上述流程，调试极难。

维度 Polyrepo Monorepo
代码复用 困难：复制粘贴或发私有 npm 包 容易：本地物理路径引用，修改即生效
依赖管理 分散：各仓库各自维护 package.json，版本参差 统一：根目录控制核心版本，消除「依赖地狱」
开发流程 繁琐：跨库开发需 link 或发包 顺畅：无需发包，保存即热更新
工程配置 重复：每个仓库都配一遍 ESLint、Jest、CI 复用：根目录定义一套规范，所有子包继承

典型例子：Google、Vue 3、React；字节、美团、阿里的中台业务线与组件库。

10.3 包管理器对比

特性 pnpm ⭐ Yarn (v1 / Berry) npm

幽灵依赖 严格禁止（安全） 宽松 存在隐患

① 磁盘机制（硬链接）

  • npm / yarn：有几个项目就复制几份依赖到各自的 node_modules。
  • pnpm：用**硬链接（Hard Link）**只下载一份到磁盘全局，其他项目全部指向它。
  • 硬链接特点：同一个文件多个入口，修改任意一个全部生效；删除其中一个链接，原文件仍在。

② 幽灵依赖（Phantom Dependencies）

  • 现象：A 依赖 B，B 依赖 C。在项目 A 中直接使用 C 不会报错，但 package.json 里没写 C。
  • 危害：若 B 后续不再依赖 C，代码立刻报错。
  • pnpm 的解法：通过非扁平化的 node_modules 结构，物理层面彻底屏蔽幽灵依赖。

10.10 编译原理：Babel

Babel 是什么

  • 一个标准 LISP 风格编译器，本质是 JS 编译器。
  • 用处：代码降级、polyfill、多端编译（Taro）。

编译的本质：把源代码加工成新代码（字符串操作）。通过词法、语法、语义分析加工代码，输出目标代码。
AST（Abstract Syntax Tree）：描述代码结构；类比 DOM 树描述 DOM 结构。

四阶段架构

① 解析（Parsing）—— @babel/parser
把非结构化字符串转为结构化数据，分两个子阶段：

  • 词法分析（Lexical Analysis / Tokenization）
    • 机制：扫描器逐字符读取源码，移除空白与注释，切割成 Token 流。
    • 形态：const a = 1 → [Keyword(const), Identifier(a), Punctuator(=), Numeric(1)]
    • 重难点：处理上下文相关语法（JSX、TypeScript）需按上下文切换 Tokenizer 状态。
  • 语法分析（Syntactic Analysis）
    • 机制：按 ECMAScript 语法规则把 Token 流组装成 AST。
    • 形态：Token 流 → JSON 树结构（符合 ESTree 规范）

② 转换（Transformation）—— @babel/traverse
最复杂、最核心的阶段，也是插件唯一介入窗口。

  • 机制：接收 AST，做深度优先遍历（DFS）。
  • 架构：采用访问者模式（Visitor Pattern），解耦「数据结构（AST）」与「操作逻辑（插件）」。
  • 形态：AST → Modified AST（被增删改查后的新树）

③ 生成（Generation）—— @babel/generator

  • 机制：深度优先遍历转换后的 AST，按节点类型递归输出字符串。
  • 代码还原：把 AST 节点转回 JS 代码。
  • SourceMap 生成：利用 AST 中保留的 loc（行列信息）映射回源码。

④ 最小流程

完整工程流程（src → compile.js → dist）

插件化体系（微内核）

  • 本质：一个 Babel 插件就是 Visitor 对象的工厂函数。Babel 遍历 AST 时每走到一个节点，就去查找所有已注册插件中是否定义了针对该节点类型的钩子。
  • 插件：arrowFunctionPlugin（语法转换）、declarePlugin（声明插件）。
  • 预设（Preset）：把多个 plugin 打包在一起。如 @babel/preset-env——把箭头函数转为普通函数、把 const 转为 var。

访问者模式的三条规则

  • 生命周期：每个节点经历两次访问——Enter（向下遍历、触达时触发，大部分逻辑写这里）、Exit（向上回溯、离开时触发）。
  • 插件在预设之前运行。
  • 插件顺序：从前向后（First to Last）；预设顺序：从后向前（Last to First，为兼容性，先跑 loose 模式）。

写一个插件的流程：参考 transform-arrow-functions 实现 → 解析源码时把插件文件路径注册进去 → 安装即可。

10.11 实战：类飞书多维表公式编译器 + AI Agent 化

四步走（以 sum(a, b) 为例）

  1. 拆：sum ( a b ) —— 拆的过程就是词法分析（Tokenizer）。
  2. 转：转为标准 AST（DSL）—— Parser。中间可先转逆波兰式。
  3. 生成：Generator。
  4. 执行：Interpreter。

AI 公式编辑器的两条路线

路线 流程 风险
传统思路（Copilot） 用户输入「计算平均值」→ LLM 返回代码 → 扔进 eval 危险且不可控，存在注入风险
高阶思路（Agentic Flow） ① Generate：LLM 基于我们的 DSL 文法生成公式② Validate：复用 parse() 作为校验器③ Reflect：parse() 报语法错误时，把错误信息回传 LLM 让其重生成④ Execute：只有通过校验的公式才送进 Interpreter⑤ 返回结果⑥ 可视化结果 可控、可解释、可迭代

这个模式可迁移到所有「LLM 生成结构化产物」的场景：先约束文法 → 再让模型生成 → 用编译器校验 → 失败回传重试 → 最后才执行。这就是「给 AI 加一层枷锁」的低代码思路。

14.1 三个必须先分清的概念：容器、编码、协议

一句话：容器管「怎么装」，编码管「怎么压」，协议管「怎么传」。

层 职责 例子
容器 Container / Muxer 把视频流、音频流、字幕、元数据打包成一个文件，并写时间戳索引 .mp4 .mkv .flv .webm .ts
编码 Codec 把原始画面与声音压缩成码流 H.264、H.265、VP9、AV1、AAC、Opus
协议 Protocol 决定码流怎么切块、怎么传输 HLS（.m3u8 + .ts）、DASH、RTMP、WebRTC

核心结论：同一个 mp4 里可以放 H.264，也可以放 H.265；同一份 H.264 码流既能装进 mp4，也能装进 flv。容器与编码是两个正交维度——这是这块最常被追问的点。

WebM VP8 / VP9 / AV1 Opus / Vorbis Web 端开源方案 Chrome / Firefox；Safari 17+

MKV 几乎任意 几乎任意 本地播放、多音轨多字幕 不支持

转封装 ≠ 转码（这块最省钱的一条经验）

  • 转封装：-c copy，只换盒子不重新编码，秒级完成、零画质损失。
  • 转码：-c:v libx264，解码再编码，慢且必然有损。
  • 判断顺序：先 ffprobe 看源编码 → 与目标容器兼容就直接 -c copy。

14.2 像素、色彩与压缩参数

像素格式（pixel format）——决定一帧画面在内存里怎么排。

格式 含义 每像素位宽 典型用途
yuv420p 亮度全采样，色度 2×2 下采样 12 bit 通用分发格式，H.264 硬解底线
yuv422p 色度水平减半 16 bit 采集卡、专业中间格式
yuv444p 色度不降采样 24 bit 抠像、色彩处理、无损
nv12 YUV420 的 UV 交错变体 12 bit 硬件编解码 / GPU 纹理
rgba 四通道 8 位，带 alpha 32 bit Canvas / WebGL、需要透明

为什么用 4:2:0：人眼对亮度敏感、对色度迟钝，扔掉 3/4 的色度信息，体积直接砍一半而肉眼几乎无感。

RGB 与 YUV 的换算（BT.601 全范围，前端最常用）

BT.709 的系数是 0.2126 / 0.7152 / 0.0722——系数用错，就是「偏色」的第一大原因。

14.5 滤镜系统：线性链与非线性链

两套滤镜入口，先分清再动手：

维度 简单滤镜 -vf / -af 复杂滤镜 -filter_complex
输入数 1 多
输出数 1 多
链内分隔符 逗号 , 逗号 ,
链间分隔符 无（一条链） 分号 ;
典型场景 缩放、裁剪、加字幕、加文字 画中画、多路拼接、混音、多输出

非线性链的语法：[输入标签]滤镜=参数,滤镜=参数[输出标签]

  • [0:v] 第 0 个输入的视频流，[0:a] 音频，[0:s] 字幕
  • 每条链 = 输入标签 → 滤镜序列 → 输出标签
  • 没被下游消费的输出标签，由 -map 决定落到哪个输出文件

四条必踩的坑

  1. -vf 与 -filter_complex 同时写，且抢同一条流——会报 Filter ... has an unconnected output。统一用 -filter_complex。
  2. 造了标签却没 -map——输出文件里干脆没有这条流，静默成功。
  3. 表达式里的逗号没转义——被当成滤镜分隔符，报参数错误。写成 \,，即使在双引号内。
  4. scale 的宽高必须偶数（yuv420 要求），用 -2 而不是 -1（-1 可能算出奇数）。

背景：Canvas 只给你 RGBA（sRGB，pc range），而视频编码器吃 YUV420P（tv range）。中间有三种对接路线。

方案 怎么拿帧 谁负责转 YUV 适用场景
MediaRecorder + Canvas canvas.captureStream() 浏览器内部 纯录制，无需精修

方案 A：交给 FFmpeg 转（最省事）

方案 B：自己算 RGBA → YUV420P（BT.601 全范围，与 14.2 的公式一致）

把帧写进编码器

背压要点：ff.stdin.write() 返回 false 时说明管道满了，必须等 drain 再写下一帧，否则内存会被帧数据堆爆。

偏色的三个根因

现象 根因 修法
整体发灰、黑色不黑 range 不一致（把 pc 当 tv 解码） 声明 -color_range，或用 scale=in_range=full:out_range=tv

14.9 踩坑与经验

  1. 参数位置错 → 静默失效：输出参数写在 -i 之前会被当成输入参数，命令照样成功，结果完全不对。
  2. copy 切片起点不准：只能在关键帧切，起点会前移；要精确就重编码。
  3. 压完反而更大：源已是高压缩低码率，再压只会更差；或根本是 -b:v 设得比源码率还高。
  4. 奇数分辨率报错：yuv420p 要求偶数，用 scale=1280:-2，必要时补 pad=ceil(iw/2)*2:ceil(ih/2)*2。
  5. Web 上拖进度条很久才出画：缺 -movflags +faststart，moov 在文件末尾。
  6. Windows 下滤镜报参数错：路径冒号写 C\:/，表达式逗号写 \,。
  7. 批量任务不要拼 shell 字符串：用 execFile('ffmpeg', [...]) 传数组，避免空格与注入。
  8. 并发要限流：x264 默认吃满所有核，N 个并发必须 -threads 或队列串行，否则整机卡死。
  9. 失败了先看 stderr 末尾：-loglevel error 只留关键报错，比翻几百行 banner 快得多。
  10. 转码是 IO + CPU 双高：容器里要限 CPU、给足临时盘、设超时，避免僵尸任务堆积。

一句话总结：换不换容器看 -c copy，画质好坏看 -crf 与 -pix_fmt，复杂效果看 -filter_complex，偏色看 color_range 与 colorspace。

  • 本质：把 LLM、Agent、插件、工作流、触发器、知识库、记忆整合成一个平台。
  • 六大模块：插件化抽象复用逻辑 → 工作流自动化编排 → 触发器驱动 → 知识库检索 → 记忆维持上下文 → 输入输出闭环。
  • 业务流程：用户输入 → 引擎编排 → 模型 / 知识库 / 插件协同 → 流式输出。
  • 三种前端集成方式：iframe、API、Agent 商城式发布。
    → §3.4、§2.2

Q2｜是否有过自动化、批处理或生成式 AI 相关业务？说说对流程引擎的理解和整体方案

  • 自动化 / 批处理核心：重复性任务、抽象层次高，把期望的任务列成步骤逐步执行。
  • 生成式 AI 的区别：用户控制整个流程，AI 去具体实现（搜索 → 提关键字 → 清洗 → 给模型分析 → RAG 优化 → 循环 → 判断）。
  • 流程引擎三要素：流程建模（编辑器）、任务调度（异步 / 依赖 / 变量上下文）、插件化集成外部系统。
  • 实现分型：内存型（前端全量执行）、服务端型（OA 审批、低代码、大数据平台）、生成式 AI 引擎（调模型、参数召回、上下文缓存、向量库操作）。
    → §6.1、§6.6

Q3｜开发一个类似飞书文档的知识库，文档编辑如何设计？重点说原理与技术实现

  • 核心清单：基础编辑、文本格式化、多媒体插入、undo/redo、跨浏览器兼容、协同、AI 赋能。
  • 三条技术路线：contenteditable 裸做 → execCommand（过时）→ Selection + Range + Compiler（推荐）。
  • Compiler 解决的核心问题：反复点击导致标签无限嵌套，需要判断已有修饰并做「加强 / 还原」。
  • 数据层：Markdown 路线性能好约束强；JSONContent 路线更灵活，自定义节点方便（TipTap custom node）。
  • 通用协议：Schema / DSL 承载物料体系（BlockSuite）。
  • 个性化：/ 命令、@ 提及、协同光标、力导向图谱、命令栈 undo/redo。
    → §7.2、§7.3

Q4｜了解过服务端渲染吗？为什么当下 AI 辅助编程首选服务端渲染方案？

  • 先讲演进：EJS/JSP → SPA → SSR + SPA 结合。
  • 再讲 AI 特殊性：追求短平快（全栈一体）、隐私与安全（token 不能落前端，否则可被任意调用）、动态与个性化。
  • 三点优势：体验（首屏）、减轻客户端压力、降低维护成本。
  • 补充类比项目：Coze、Dify 这类平台，以及 v0、bolt 这类生成式产品。
    → §8.1、§8.2、§8.3

Q5｜简单描述协同文档编辑器的方案和核心实现

  • 分层：编辑器内核（TipTap / ProseMirror）+ 协同算法（CRDT / OT）+ 具体实现（Yjs / Automerge）+ 传输（WS / WebRTC）+ 服务层（Node / NestJS / Redis / Kafka）+ 存储（PostgreSQL + pgvector）。
  • 关键判断：CRDT 分布式友好，OT 依赖集中式；Yjs 是当前首选。
  • 实现五步：建 Y.Doc → 绑定编辑器 → 实时通信 → 光标同步（Awareness）→ 后端接入。
  • 依赖清单要能报出来：@tiptap/extension-collaboration 是绑定层。
    → §7.4、§7.5

Q6｜有没有做过 AI 相关业务？说说 AI 大模型应用开发的核心方向和重要技术点

  • 三个方向：AI 原生应用、AI 赋能已有业务、AI 应用开发平台。
  • 四大技术：LLM（概率预测、涌现、上下文依赖；基础模型 vs 微调模型）、Prompt 工程（角色 / 思维链 / 结构化输出 / 指令数据分离）、RAG（索引 + 查询两阶段）、Agent（ReAct + 工具 + 过程可视化 + 交互干预）。
  • 选型三关注：上下文窗口、成本（token 计费）、响应速度。
  • 前端两个黄金点：流式渲染、引用溯源。
    → §3.2、§2.3、§2.4、§4.1、§4.2

Q7｜做过前端监控？性能与异常监控指标是怎么算的？

  • 性能：PLT、FP/FCP、FMP、LCP、TTI、CLS（≤0.1 良好）、INP。
  • 异常：JS 运行时、Promise unhandled rejection、资源加载、接口请求、React/Vue 框架异常。
  • 行为：PV、UV、点击/操作、停留时间；新老用户用 Cookie 标记。
  • 上报：fetch/XHR（CORS 解决跨域）、图片打点、sendBeacon。
  • 工程化指标：构建时间、缓存利用率。
    → §9.1、§9.2

Q8｜前端 AI 这块做过什么？了解过私有化 AI 平台部署和应用吗？

  • 回答框架：技术广度 + 工程化能力（私有化部署）+ 业务思考。

  • 收尾升华：从「平台构建者视角」讲清人设、插件、知识库、工作流如何协作。

Q10｜你 TS 掌握得怎么样？TS 与 Zod 为什么在 Agent 开发中应用广泛？前端往 Agent 能有哪些沉淀？

  • TS：编译时静态检查，约束框架契约与协议数据结构。
  • Zod：运行时校验，做入参标准、输出结构化、参数提取 schema、工具入参防护。
  • TS 重点：基础类型/别名/接口、联合与交叉（面向协议编程）、类型守卫（类型收敛）、工具类型（Omit/Pick/Partial）、泛型与类型体操。
  • 前端三点沉淀：TS AI SDK 工程化、Node/Nest/Nuxt 服务化、Prisma + PostgreSQL 持久化。
    → §13

Q11｜有没有参与过工作流编辑器开发？简述工作流类型、技术选型与实现细节

  • 三种类型：线性流、DAG（AI 最常用，严禁环路）、状态机流。
  • 选型：SVG（React-Flow/X6，首选）vs Canvas（LogicFlow/LiteGraph，超大规模）vs 纯 DOM（上手快但连线难写）。
  • 四个细节：数据协议（兜底/降级/拓展/升级）、引擎实现三选一、节点边物料体系（插件化/微内核）、协同 + 执行（建图、遍历、异步、日志、错误收集）。
  • 面试建议：以 React-Flow / AntV X6 切入，强调可定制插件系统。
    → §6.2、§6.5

Q12｜了解过什么服务端框架？最快实现 AI 全栈 POC，技术栈怎么选？

  • 四层架构图：前端交互层 → AI 核心能力层 → 数据持久化层 → 部署环境层。
    → §5.6、§12

Q23｜设计过大型实时数据流系统？详细说明监控平台的方案设计与落地

Q27｜怎么实现通用工作流编辑器与工作流执行引擎？说说内存型与服务型的顶层设计

    → §6.6

Q46｜站在前端架构师角度，说明协同编辑器原理、Yjs 实现，以及 CRDT / OT 的概念与实现

  • OT：中心服务器 + 版本校验 + Transform(OpC, OpA) 转换（要能画出时序图）。
  • CRDT：生成 Update → 中转 → 本地合并；面向状态 vs 面向操作。

  • 优缺点各两条（元数据开销、意图保留问题）。
  • 结论：首选 CRDT，OT 在敏捷、高可用、离线体验面前已不合时宜。
  • 附带技术储备：算法、3D 数字孪生（WebGL/WASM、正射影像与倾斜摄影、Tile 与模型处理、PBR 与粒子）、全面性能优化（打包构建、资源、应用、缓存四层）。

16.5 高频追问速答表

追问 一句话答案
CRDT 还是 OT？ 首选 CRDT：去中心化、支持离线、服务端轻；OT 转换函数太复杂且强依赖中心服务器
内存型还是服务型工作流？ 前者快、无持久化，适合前端预览；后者可断点续传、能人工审批，适合长链路业务
SSE 还是 WebSocket？ 单向流式推送用 SSE（简单、自动重连）；需要双向或低延迟交互用 WS
pnpm 为什么快？ 硬链接只存一份 + 非扁平结构屏蔽幽灵依赖
Turborepo 凭什么快？ 任务管线 + 本地/远程缓存命中，只重跑受影响的包
ClickHouse 为什么适合监控？ 写多读少、按时间聚合；列存 + 向量化执行，亿级 Group By 秒级出结果
为什么要 Kafka？ 解耦生产与消费速度，削峰填谷；按 session 分区保时序
为什么选 SSR 做 AI 应用？ token 不能落前端 + 首屏与 SEO + 全栈一体提效
沙箱怎么选？ 强隔离用 Docker（慢）、轻隔离用 WASM（快）、进程内用 vm2/isolated-vm（需谨慎）
前端在 Agent 里的不可替代性？ 过程可视化、人机干预、流式渲染、引用溯源——全是前端活
LCP / CLS / INP 分别衡量什么？ 加载性能 / 视觉稳定性（≤0.1）/ 交互响应速度
LangChain 和 LangGraph 怎么选？ 线性简单用 LangChain，有状态、分支、循环、可恢复用 LangGraph
为什么提示词要结构化输出？ 免去字符串解析，直接绑定状态，前端最实用的一招
低代码为什么能约束 AI？ DSL 相当于给 AI 加一层枷锁，生成物可被编译器校验后再执行

16.6 案例 A：项目介绍模板（可直接背）

适用于「公司 AI 项目从立项到落地你参与了多少」这类题。结构固定：立项阶段（业务产出 + 技术产出）→ 研发落地阶段（业务产出 + 技术产出）→ 技术资产沉淀。

作为前端 Leader，我深度参与了公司级 AI 项目「智能合同分析助手」的全链路过程，主要产出如下：

立项阶段（参与度 80%）

  • 业务产出：
    • 与法务、销售团队共同做需求访谈，识别核心痛点：审查效率低、风险点易遗漏。
    • 主导编写产品原型与交互设计稿，通过可交互 Demo 向管理层展示核心价值与体验，成功推动立项；强调「信息高亮」「风险可视化」「人机协同修订」等前端交互价值点。
  • 技术产出：
    • 技术预研（PoC），与后端架构师共同验证「RAG + 少量微调模型」方案的可行性。
    • 输出《前端技术选型报告》，确定 React + SSE 技术栈，并预估人力成本与时间线。

研发与落地阶段（参与度 100%）

  • 业务产出：
    • V1 上线后，法务团队单份合同平均审查时间从约 45 分钟缩短至约 15 分钟。
    • 上线「风险条款一键定位与解释」功能，用户满意度约 95%。
    • 与产品经理共同制定 V2 Roadmap，规划「多版本合同对比分析」等高级功能。
  • 技术产出：
    • 主导前端架构：采用「文档 - 视图 - 控制器」分离。文档层负责与后端流式接口通信并管理原始数据；视图层高效渲染长篇合同文本与 AI 高亮结果；控制器层处理复杂交互逻辑。
    • 攻克三个难点：
      • 长文档渲染性能：虚拟滚动，100 页以上 PDF 秒级加载与流畅滚动。
      • 高精度文本定位：与后端协作定义文本坐标体系，实现风险条款的像素级高亮。
      • 高并发流式解析：设计稳健的解析与错误恢复机制，网络抖动或响应缺失时前端平滑回退并提示。
  • 技术资产沉淀：
    • 封装内部 react-ai-stream-parser 组件库，统一处理各类 LLM 流式响应，已在公司另外两个项目复用。
    • 编写《前端 AI 应用开发规范》，统一状态管理、API 调用、错误处理的最佳实践。

收尾句：通过这个项目，不仅交付了高价值业务产品，更在团队内部建立了可复用的前端 AI 工程化体系与方法论，为后续 AI 项目打下基础。
