本篇是系列第 3 篇，讲工作流引擎架构和协同编辑。

六、工作流与 AI 应用引擎架构

本章是全篇的架构核心：所有「AI 应用平台 / 低代码 / 扣子类产品」的骨架，都是编辑器 + 执行器 + 协议。

6.1 三种平台形态

形态 实现方式 示例
无代码平台 把多个 action 串联执行，即 action flow，在前端页面自动执行，也称内存型工作流 / 内存流程引擎 Glide
低代码平台 借助工作流编排，涉及触发器、代码执行器、数据查询器、循环节点等 Retool
AI 应用生成引擎 生成式 AI 应用引擎（在传统工作流上叠加 LLM、Agent、插件、知识库） Coze、Dify
  • 无代码：glide
  • 低代码：retool
  • AI 应用生成引擎：coze
  • 本地部署：Dify（见 §3.5）

流程引擎的本质：自动化管理和执行既定的业务流程，涵盖自动化处理、批处理、AI 生成详细过程。
三大核心功能：

  1. 工作流流程建模（编辑器）
  2. 任务调度：异步处理、前后依赖、变量上下文
  3. 集成外部系统、插件化构建流程功能生态

6.2 常见工作流类型

  • 线性流（Sequential）：最简单的逻辑，节点按 A → B → C 顺序执行。
  • 有向无环图（DAG）：AI Agent 最常见的形态，允许分支与回合，但严禁形成环路（会死循环）。
  • 状态机驱动流（State Machine）：侧重状态流转（审批通过、驳回、待补件），每个节点是一个状态，连线即触发动作。

6.3 节点体系

核心节点

节点 作用 配置要点
start 节点 工作流起点，由外部事件或用户输入触发 字段类型（文本/段落/下拉/数字）、变量名称、显示名称、最大长度、是否必填
模型节点 调用生成式 AI 模型做生成或理解 选择模型与参数（温度、Top P、存在惩罚、频率惩罚、最大标记、回复格式、停止序列）、上下文、提示词、记忆（记忆窗口）、输出变量
知识检索节点（可选） 检索已有知识库 查询变量（自动带入 start 变量）、知识库（选一篇或一个文件夹）、输出变量
条件节点 分支控制 if 区域可加多个条件；else 区域直接显示描述词
代码执行节点 自定义逻辑 输入变量（初始两个「名 / 值」，可增删改）、代码编辑器（可直接使用输入变量）、输出变量（变量名 + 类型）
直接回答节点 相当于当前最后节点，但仍可继续下一步 回复文本域可拿到所有回复节点的字段
更多节点 模板转换、变量聚合器、参数提取器、迭代、问题分类器、HTTP 请求（可写入飞书多维表格等） —

扩展节点类型（平台生态视角）

  • 插件节点：调用外部插件完成集成型任务（天气查询、支付处理）。
  • 业务逻辑节点：执行条件判断或复杂算法（如选择支付时触发支付流程）。
  • 子工作流节点：把一个工作流嵌套进另一个工作流，支持递归调用，提升可重用性。
  • 结束节点：所有任务执行完毕，返回最终结果。

交互细节：每个节点连接下一节点时，右键可拿到当前节点可连接的所有节点（即类型校验后的候选集）。

6.4 数据协议与 DSL

两大构成要素

  • 节点（Node）：定义功能。
  • 边（Edge）：定义来源（from / source）与目的（to / target），约束节点关系与流程。

DSL（Domain Specific Language） 领域特定语言，可与 AST（Abstract Syntax Tree） 结合使用。

假设有三个节点：触发器 trigger、新建标签页 newTab、滚动执行器 scroll，从左往右连接成有向无环图。

协议设计四要求：数据兜底、降级、扩展、升级。

6.5 编辑器技术选型

选型方向 代表库 优点 缺点 适用场景
原生 SVG React-Flow / X6 矢量不失真，易用 CSS 控制样式，DOM 节点易绑事件 节点过多（数千）时有性能瓶颈 首选：中小型 AI 工作流、低代码平台
Canvas LogicFlow / LiteGraph 性能上限极高，适合超大规模节点 开发成本高，节点交互需手算坐标（Hit Testing） 大型工业监控、超复杂逻辑链路
纯 DOM / HTML 自研 上手最快，可用原生拖拽 API 连线算法（SVG Line）极难写，维护成本高 简单的垂直线性审批流

面试建议：以 React-Flow 或 AntV X6 为切入点，强调其高度可定制的插件系统与成熟生态。

工作流开发的四个细节

  1. 数据结构定义 → 引擎数据协议设计（兜底、降级、拓展、升级）。
  2. 引擎实现：Canvas、SVG、自研框架 三选一。
  3. 节点 / 边定义与灵活拓展 → 物料体系灵活接入，基于插件化 / 微内核机制（可对接远程插件市场、MCP）。
  4. 编辑器协同 + 执行引擎实现：协同用 CRDT / OT 解决冲突；执行要处理建图、遍历、异步、日志、错误收集。

6.6 执行器：内存型 vs 服务型

维度 内存型工作流（In-memory） 服务型工作流（Service-based）
执行环境 浏览器端或单个 Node.js 进程内存 分布式微服务集群
状态存储 随进程结束释放，瞬时性 数据库持久化（MySQL / Redis），支持断点续传
适用场景 前端低代码预览、轻量 AI 助手、单纯数据转换 复杂审批流（需人工参与）、长时耗任务、支付链路
核心挑战 内存溢出与性能：节点过多导致浏览器卡死 幂等性与重试：节点执行一半服务宕机如何恢复

内存型执行机制

  • 顶层设计：典型的事件驱动模型。
  • 运行逻辑：引擎把整个 Graph 加载进内存，通过递归或循环消费任务队列。
  • 关键点：快照同步（每行执行完直接更新 UI 状态）、轻量化（无需考虑网络延迟，节点间数据传递用引用或简单 Copy）。

服务型执行机制

  • 顶层设计：任务队列 + 状态机持久化（类似 Temporal、Camunda 的简化版）。
  • 运行逻辑：
    1. 任务解耦：引擎把待执行节点推入消息队列（RabbitMQ / Redis）。
    2. Worker 消费：不同 Worker 认领任务并执行，结果写回数据库。
    3. 状态脱水与复活：需要「人工审批」的节点，引擎把流程挂起（Wait），上下文脱水（Serialize）入库，触发后再复活（Hydrate）。
  • 关键点：必须处理分布式事务与超时重试。

6.7 执行器实现：从最小闭环到生产可用

① 最小实现（内存型）

编辑器 + 执行器都在前端时，三步走：

  1. 约定流程协议（节点与边的 JSON 数据）。
  2. 编辑器编排工作流数据。
  3. 开发执行器：从前到后按序执行，后面的节点可以拿到前面节点的上下文，通过链表串联。

② 生产级三项增强

1）完全稳定可靠的日志系统（基于异步实现）
在每个节点执行前后记录：节点开始时间、输入与输出数据（敏感数据需加密或遮盖）、执行状态（成功 / 失败）、错误信息。

2）上下文变量池

  • 在整个流程执行期间保持全局有效，存储所有必要的状态信息。
  • 内容包括输入数据、计算结果、外部调用响应等。
  • 每个节点执行时，执行器按需从池中取数据或更新数据。

3）错误处理机制

  • 全局错误捕获：兜住所有未处理错误并记录相关信息。
  • 节点级错误处理：每个节点可定义自己的错误策略，如 API 报错重试。
  • 错误通知：关键节点出错时通知管理员或用户。
  • 错误恢复：可恢复错误（如网络请求）设计重试机制。

6.8 平台级架构：以 Coze 为例

从「单体作坊」到「工业化生产线」
开源的 coze-studio 用 Docker Compose 把所有功能打包在一起，适合快速体验和中小团队；要支撑大型企业或公有云，必须转向云原生、微服务化架构。

设计理念：「一个中心，四大体系」

  • 一个中心：AI 编排与执行引擎（AI Orchestration & Execution Engine）——平台心脏，负责解析和运行由节点（Nodes）与边（Edges）组成的业务流程图（Workflow DAG）。
  • 四大体系：
    • a. 应用构建体系：面向开发者，提供极致体验的前端编排界面、调试工具与版本管理。
    • b. 插件生态体系：平台能力扩展的基石，通过标准化 SDK、市场和沙箱环境，赋能开发者贡献工具。
    • c. 多租户与数据管理体系：企业级服务基座，负责用户、组织、权限、数据隔离与知识库向量管理。
    • d. 可观测与运维体系：日志、监控、告警与成本分析。

微服务拆分（服务间推荐 gRPC 内部通信，API Gateway 统一对外提供 RESTful / GraphQL）

服务 职责 与 coze-studio 的对应关系
API 网关 所有外部请求的统一入口，负责鉴权、路由、限流、协议转换。选型：Kong、Traefik、Spring Cloud Gateway —
用户与租户中心 用户、组织（租户）、角色权限（RBAC），登录注册、SSO 单点登录 coze-studio 只有简单的用户概念，需增强为企业级多租户模型
Bot 配置中心 核心 CRUD：Bot 的创建/读取/更新/删除，含人设（Prompt）、插件配置、工作流静态定义（通常是一个大 JSON） coze-server 中处理数据库交互的大部分逻辑
插件市场服务 插件生命周期：注册、审核、发布、版本控制与发现；存插件元信息（manifest：名称、描述、输入输出 schema） —
数据与向量管理服务 解耦底层数据库，对上层提供统一数据访问；内部封装 PostgreSQL（业务）与 PGVector / Milvus（向量）；负责知识库文档的切分、向量化、存储 —
AI 编排与执行引擎 无状态计算服务：接收 Bot 配置中心传来的工作流 DAG，负责实时执行、状态追踪与结果返回。性能与稳定性的关键 —

6.9 前端编排 + 后端执行的关键难点

前端编排引擎：本质是一个面向 AI 工作流的、可视化的 DAG 编辑器。

  1. 状态管理与交互：用户拖拽节点（工具、LLM、判断逻辑）并连线，实时构建复杂图结构。需要强大的状态管理方案（Redux Toolkit、Zustand）维护完整数据结构——每个节点的位置、配置与连接关系。
  2. 图结构序列化：点击「调试」或「发布」时，前端必须把可视化图序列化成后端执行引擎能理解的标准 JSON，描述拓扑结构与每个节点的具体参数。
  3. 实时调试反馈：调试模式下后端逐节点执行时，前端要实时高亮当前节点并显示输入输出。这要求前后端建立长连接（WebSocket 或 SSE），由后端主动推送执行状态与日志。

后端流式节点执行引擎：整个架构的「技术之巅」。用 for 循环按序执行是天真实现，低效且无法处理流式输出。工业级引擎必须解决：

  1. DAG 解析与执行调度：拿到工作流 JSON 后先做拓扑排序，确定执行顺序，并识别可并行执行的分支。
  2. 异步非阻塞 I/O：几乎所有节点（调 LLM、调 API、查数据库）都是 I/O 密集型，引擎必须完全异步非阻塞（Node.js 事件循环，或 Go 协程）。
  3. 流式处理（Streaming）：LLM 节点不能等全部生成完再返回。
    • 调用大模型时明确要求流式返回（如 OpenAI API 的 stream: true）。
    • 引擎收到的是数据流而非完整响应。
    • 通过 WebSocket / SSE 把每个数据块（token）实时转发给前端，实现打字机效果。
    • 同时把数据块拼接成完整输出，作为下一节点的输入。
  4. 安全沙箱（Sandbox）：执行社区开发者贡献的代码片段或插件时，绝不能在主服务直接运行。
    • 方案一（重隔离）：为每个任务动态启动轻量 Docker 容器，隔离最好但冷启动慢。
    • 方案二（轻隔离）：WebAssembly（WASM），启动极快、安全性高，是很有前景的方向。

工程化闭环五步：① 定义 DSL → ② 编辑层（状态管理 + 插件化架构）→ ③ 执行器（拓扑排序与动态调度、沙箱隔离）→ ④ AI 特化设计（变量提取与上下文流转、流式输出）→ ⑤ 测试与工程化闭环。

6.10 沙箱的两层理解

  • 记忆方式： 通过费曼学习法，记住一个，根据另一个进行推导。
  • 微前端沙箱（如 qiankun 的三种 sandbox）：legacy sandbox、proxy sandbox、snapshot sandbox，目的在样式隔离、JS 隔离。
  • 系统级沙箱：目的是系统环境隔离，保证执行安全性。deepagent 涉及文件操作、bash 执行、shell 提权，必须做隔离。
  • 服务端隔离强度排序：Docker 容器（强隔离、冷启动慢）→ WASM（轻隔离、启动快）→ vm2 / isolated-vm（进程内隔离，性能好但需谨慎使用）。

七、协同编辑

协同系统的中级目标是维护多方数据的一致性。
本文只关注上层的数据同步与冲突处理；下层传输与持久化不是重点，可用 WebSocket 或其他方案替代。
编辑器内核选型：重量级代码编辑器（VS Code、Trae）用 Monaco Editor，其余多选 TipTap。

7.1 协同场景盘点

产品形态 协同数据特征 技术组合
协同文档（飞书文档、Notion） 带格式的、流式文本内容 TipTap（视图层）+ Yjs（数据模型）+ y-websocket（通信层）
协同代码编辑器（VS Code、Trae） 纯文本，对性能、语法高亮、开发体验要求极高 CodeMirror + Yjs + y-codemirror.next + y-websocket
可视化图表编辑器 结构化图表配置 智能协同可视化编辑引擎
在线白板（博思白板、飞书画板） 画布元素、层级、位置 画布引擎 + CRDT
协同视频编辑器（剪映） 时间轴轨道、片段属性 时间轴模型 + CRDT
多维表格（飞书云表格） 单元格、行列结构、公式 类 Skia/Canvas 渲染 + CRDT + 公式引擎
数字孪生低代码（DataWind） 组件树、场景图、节点属性 Vue3 + WebAssembly + VanillaJS
协同 AI 应用引擎（扣子） DAG 节点与边、配置 图协议 + CRDT

7.2 编辑器内核与格式化实现的三种路线

竞品参考

  • 飞书文档、Notion：丰富的文本格式、多媒体嵌入、实时协作；可用快捷命令（/、@）快速插入不同类型的块（Block）。
  • Google Docs、Word Online：复杂文档编辑能力——文本格式化、插图、撤销重做、表格与绘图。
  • Quill、Draft.js：开源富文本编辑器，可二次开发自定义方案，支持插件扩展与丰富 API。

文档编辑的核心清单
基础编辑、文本格式化、多媒体插入（图片、视频、@提及、引用跳转）、undo/redo（含 Ctrl+Z）、跨浏览器兼容、协作（协同）、AI 赋能。

① contenteditable 属性
在任意容器上设置该属性即可变为可编辑容器；可编辑容器内也可内嵌多个容器，不想编辑的部分设为 contenteditable="false"。

② 路线一：浏览器 execCommand（小白级，过时 / 即将废弃）

  • document.execCommand 是浏览器 API，用于在 HTML 文档中执行与内容相关的命令。
  • 缺点：兼容性差、可维护性差。

③ 路线二：Selection + Range + Compiler（大神级）

  • 单独用 selection（获取当前选中内容）+ range（精确操作选中内容）时会发现：每点击一下就被新的标签包裹。Compiler 负责切换——判断当前内容是否已有修饰标签，是则还原，否则添加修饰。
  • 大部分编辑器都提供编译器：Markdown / MDX 有 hyper，TipTap 类基于 JSONContent 结构。取舍：
    1. 基于 Markdown：性能更好、约束更强。
    2. 基于 JSONContent：特性更灵活，自定义节点更便捷（如 TipTap custom node）。
  • 内容 → 可存储格式 → 再解析回来：实现 JSON 与 HTML 双向转换，可参考 html2json。
    • HTML 转 JSON：递归遍历 DOM 元素，构建结构化 JSON。
    • JSON 转 HTML：从 JSON 数据生成 HTML 字符串，支持富文本格式。

④ 通用数据协议
用 Schema / DSL / 协议数据承载整个应用的物料体系，参考 BlockSuite。

7.3 个性化需求：@ 提及与 / 命令补全

其他常见个性化能力

  • 协同光标：前端用 WebSocket 实时通信，每个客户端收发光标位置与编辑内容；后端 WebSocket 服务器接收消息并广播给其他客户端，保证编辑状态一致。其他方案：Yjs 等。
  • 知识图谱：graph、d3 forceGraph（力导向图）。
  • 历史记录栈与 Undo/Redo：用命令模式 + 历史栈管理用户操作，把命令对象压栈；撤销时弹出最后一个命令对象并调用 undo，重做时调用 redo。
  • 跨浏览器兼容：不同浏览器对 Range/Selection 的实现差异，是编辑器落地的主要坑之一。

7.4 协同架构：协议先行

协同前置，协议先行。

① 传输协议：WS、Socket.IO（下层也可用 WebRTC）。

② 协同数据分两类

  1. 交互式数据（业务无关）：头像、光标位置。
  2. 核心业务数据：文档内容、图结构、单元格数据。

③ 数据冲突与两大理论

  • OT（Operation Transformation，操作转换）：Google Docs、Etherpad 使用。集中式，强依赖中心服务器。
  • CRDT（Conflict-free Replicated Data Type，无冲突复制数据类型）：分布式友好，天然支持 P2P 与离线编辑。
    • 进一步分类：面向状态的（state-based）、面向操作的（op-based）。

④ 协同方案对比

  • Yjs：基于 CRDT，支持实时同步与冲突处理，生态最成熟。
  • Automerge：偏 OT 思路，支持同步与冲突处理，但实时编辑体验较弱。
  • 附录：CRDT 论文及实现方案

⑤ 服务层与存储

  • 服务层：Node、NestJS、Redis、Kafka + ClickHouse（数据量大时使用）。
  • 数据库：PostgreSQL（AI 向量化用 pgvector）。

特性 OT CRDT

7.5 Yjs 实战

① 协同原理

② Yjs 的五个重要特性

  1. 核心数据结构：Item 与双向链表。
  2. 全局唯一 ID + 逻辑时钟。
  3. 冲突解决：确定性排序规则。
  4. 删除即标记（Tombstones）。
  5. 性能优化：Struct 与高效二进制编码。

③ CRDT 的优缺点

  • 优点：
    • 实现简单：相比 OT，核心逻辑更简单，无需编写复杂转换函数。
    • 天生去中心化：完美支持 P2P 与离线编辑，离线修改联网后无冲突合并。
    • 服务端逻辑轻：通常只扮演无状态的消息中转站。
  • 缺点：
    • 元数据开销：为保证可合并性需存额外元数据，理论上比 OT 占更多内存（Yjs 已做大量优化）。
    • 意图保留问题：极端场景无法完美保留「真实意图」——「剪切一段文本再粘贴到别处」会被看作「删除一串字符」+「插入一串字符」。绝大多数场景不构成问题。

Vue3 + WebAssembly + VanillaJS

  • 关键技术要素：IoT、AI、GIS、BIM；掌握用户故事映射等需求分析方法。

  • 编排引擎设计：独立设计低代码编排引擎的核心数据模型 DSL 与交互逻辑，具备设计与实现事件驱动、逻辑触发机制的能力。
